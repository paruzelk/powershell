# OutlookPOP3Archive 2.6.4-B2 — disposable fixture and owned Worker controller (DEV)

Development increment ONLY; requires native Windows PowerShell 5.1 CI and explicit live Outlook test review before any use. No production Archive/Resume/Auto integration. The FIX13b mail mover, protocol 1.0 allowlist and user mailbox files are unchanged.

## New diagnostic entry points

- Core/Diagnostics/New-OPA264DisposableFixture.ps1
  - Requires BOTH -Execute and -AllowTemporaryStoreMounts.
  - Only attaches to an existing Outlook process in an STA PowerShell 5.1 session.
  - Creates a unique directory directly inside the current user's OS TEMP, then calls AddStoreEx to create TWO NEW Unicode PSTs. Never accepts paths to existing PST files and never copies a real mailbox message.
  - Adds a single synthetic MailItem inside the new Source.pst, writes a full fingerprint and verifies that Outlook preserved it. Outlook builds that reject those MAPI test fields fail closed; do not weaken the requirement.
  - Persists durable MailMove Intent, request.json and LAST a scope marker. Leaves newly created PSTs mounted and preserves evidence even on failure. Does not start the Worker or move any mail.
- Core/Diagnostics/Invoke-OPA264TestController.ps1
  - Requires -Execute and an exact RunId of an already approved, complete fixture.
  - Revalidates the exact disposable PST paths and single durable Intent.
  - Creates a flushed, exclusive controller-dispatch.claim BEFORE launching one and only one test-only PowerShell 5.1 STA child. Uses the separate Core/Diagnostics/Invoke-OPA264TestWorker.ps1 entrypoint, NOT the normal WorkerProtocol allowlist.
  - Bounded timeout, parent-owned Process object only. Never kills Outlook.exe. All missing/malformed responses or timeouts classify as Indeterminate and require manual review.
  - Writes controller-result.json once. No Completed/Reconciled event and NO automatic retry, even if a process ended before Move.
- Core/Worker/WorkerTestFixture.ps1 — pure plan, fixed-path validation, no-reuse and capability contract.
- Tests/Worker/WorkerTestFixture.Tests.ps1 — 14 new offline non-COM tests.

## Safety and test policy

Use a disposable Outlook profile or isolated Windows test VM. Creating temporary PSTs modifies the CURRENT Outlook profile's set of mounted stores; created stores deliberately remain mounted as forensic evidence. Never run this diagnostic on a production RDS user session.

The expected first attempt has a controller claim and a Worker Move claim. If either claim exists, it MUST NOT be removed to reissue the same operation. Do not delete the temporary PSTs, journal, or response/report during recovery investigation.

The fixture must not be used if the Outlook object model cannot persist an InternetMessageId and sender fingerprint for a locally created MailItem. A failed fixture is NOT authorized for any worker dispatch. No imported donor PST or user mailbox should be substituted.

## Suggested explicit manual sequence, ONLY on isolated test Outlook

1. Run Windows PowerShell 5.1 CI on the exact 2.6.4-B2 source. Expected: 334 Pester tests in 29 containers, zero skipped/failed.
2. From a Windows PowerShell 5.1 STA session with an already running TEST Outlook profile, invoke the fixture creator with -Execute -AllowTemporaryStoreMounts; record the RunId and paths. No move happens.
3. Inspect the two NEW PSTs and one synthetic message in Outlook, and verify request/journal.
4. Separately opt in to the controller using the exact RunId and -Execute for the FIRST and ONLY Move. It does not prove completion; inspect evidence independently.
5. Do not run controller again for the same RunId. For a later experiment create a NEW unique fixture.
6. Future 2.6.4-C/D stages add controlled crash barriers and new-process reconciliation; do not claim recovery proof yet.

## Known boundaries

Windows CI checks syntax and offline safety logic, NOT live Outlook behavior. Synthetic writable MAPI fingerprints and AddStoreEx need real Outlook 2016/2019 validation. The current application build metadata is still 2.6.3-PREVIEW1 while B2 is stacked as a development-only change; this is NOT a new 2.6.3 release and must not be promoted until version/release metadata are aligned.
