# 2.6.5-BW3c — Windows PowerShell 5.1 Cyrillic path compatibility fix

## Confirmed BW3b runtime failure

The user ran native Windows PowerShell 5.1 CI successfully:
    PASS Pester: 880 tests in 48 containers, 0 failed, 0 skipped.
    CI PASSED.

The **first real Outlook BW3b read-only audit** then stopped at the
initial parameter check BEFORE accessing Outlook or inspecting claims:

    BW3b only audits the exact approved BW3a synthetic RunId/PST/journal SHA256.

Cause: the BW3b inspector included the literal Cyrillic source PST directory
in a UTF-8-without-BOM .ps1. Windows PowerShell 5.1 reads such a script
using its legacy ANSI code page unless BOM is present, so the hard-coded
Cyrillic portion may decode incorrectly, defeating strict -cne comparison.
The same Unicode literal was used by the previous offline test but never
compared against the native PS5.1 correctly decoded operator's -SourcePst.

**BW3c fixes the encoding bug without permitting arbitrary PST paths.**
Get-OPA265BW3bPinnedIdentity now returns the EXACT previously approved
path constructed using Unicode character codes (ASCII-only .ps1 source).
The standalone inspector compares -SourcePst against pinned.SourcePst
using the SAME strict case-sensitive ordinal PowerShell check as before.
The 43 earlier evidence tests use the same path from pinned identity.
12 NEW native PowerShell regression tests prove expected Unicode
characters, full exact path, wrong folders/case rejection, ASCII-only
scripts, guard ordering and no mail/journal mutation.
