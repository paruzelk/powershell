# 2.6.5-BW4e2 — targeted read-only MAPI lookup for a large POP3 Inbox (DEV)

## Context and immutable scope

The operator reported 26485 messages in source POP3 Inbox. Original
BW4c/BW4e1 bounded enumeration correctly rejects above 1000 by default
and above 5000 maximum. Do not raise its limit.

BW4e2 adds a separately opted-in SECOND Outlook read path:
1. Verify POP3 source PST, unique DeliveryStore, folder identity and
   MailItem using Namespace.GetItemFromID.
2. Use direct MAPI PR_INTERNET_MESSAGE_ID (Unicode property 0x1035001F)
   to build an exact, strictly syntax-bounded DASL equality restriction.
3. Call Folder.Items.Restrict with that exact filter. Require exactly ONE
   matching item; reject zero, duplicates, null or COM errors.
4. Verify the found item has exactly the previously pinned EntryID,
   Parent StoreID and FolderEntryID, PR_SEARCH_KEY SHA256, and content
   field fingerprint SHA256. No full 26485-element enumeration.
5. Report FolderItemsObserved and FolderItemsScanned separately:
   the latter remains ZERO for this explicitly targeted read.

Hard targeted bound: 1..100000 items; the separate original 1000/5000
full enumeration cap remains unchanged. Outlook Restrict availability
may vary with version/provider; unsupported filter fails closed.
No unbounded fallback or alternative mailbox/store search is allowed.
Both read paths still use ONE Outlook session; this is NOT independent
external MAPI content evidence or full PST byte-for-byte audit.

The original BW3a historic one unresolved Intent and seven immutable
evidence hashes, and all discovered LIVE3/LIVE4 journal hashes, remain
protected by the existing BW4a/BW4b/BW4c/BW4d/BW4e1 read-only pipeline.
Even exact matches NEVER give permission to Move, create a claim,
append the old journal, retry or dispatch any production Worker.
