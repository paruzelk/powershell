# 2.6.5 — bounded Archive/Resume Worker canary (DEV only)

## Scope: read-only integration barrier, not mail-move enablement

The 2.6.4 LIVE3/4/5/6a chain passed with synthetic cross-PST Move, controlled Worker crashes, independent MoveConfirmed and manual, one-shot journal Reconciled resolution.

The 2.6.5 milestone wires the EXISTING isolated worker boundary into the main OutlookPOP3Archive.ps1 Archive/Resume entry point for the **first opt-in canary**, with one read-only Ping request only. The canary stops before Outlook COM discovery, transaction creation, PST creation, archive journal, duplicate index or MailMover. It does **not** move any message, does not reuse previous LIVE4 RunIds, and does not perform Resume or Archive. This is a controlled deployment of the entry routing and worker process outcome gate, NOT real mail-move routing.

FIX13b remains the default for all modes. RELEASE.json Integration.ArchiveWorkerEnabled, ResumeWorkerEnabled and AutoWorkerEnabled remain false; RealMailMoveViaWorker=false, ProductionReady=false.

## Security/rollout bounds

The opt-in must meet ALL conditions:
- Explicit -WorkerPilot and -ConfirmDevWorkerPilot.
- Explicit -Mode Archive or -Mode Resume (Auto, Analyze, Plan are forbidden).
- -WhatIf, -Limit 1, -WorkerPilotMaxOperations 1 (strict, not a configurable wider batch).
- -ProfileName Outlook (approved test profile token; the read-only Ping DOES NOT open/validate this profile).
- -WorkerPilotTimeoutSeconds 1..30 seconds, default 10.
- Resume additionally requires explicit nonempty GUID -Transaction; this identifies intent but the canary deliberately DOES NOT touch or verify the actual checkpoint.
- Only WorkerProtocol operation Ping is allowed. No ProbeOutlook, no Worker MailMove, no user script evaluation, no Outlook COM, and NO automatic fallback to the original archive engine after pilot.
- A failed/indeterminate/invalid child response fails closed (no second dispatch, no automatic retry).
- Supplying pilot-specific parameters WITHOUT -WorkerPilot also fails closed rather than silently reverting to legacy.
- The guard runs before New-OPAComSession and before Move-OPAItemsWithLimit. The Worker canary returns immediately with a typed result.

- Schema=2.6.5.BoundedWorkerCanaryResult.1
- Status=ReadOnlyCanaryPassed, WorkerOperation=Ping, OperationsExecuted=1
- WorkerApartmentState=STA, WorkerProcessId positive, RequestId GUID
- OutlookComAccessExecuted=False, OutlookMoveExecuted=False
- ArchiveTransactionCreated=False, JournalChanged=False
- RealMailMoveViaWorker=False, AutomaticRetryAllowed=False, ProductionReady=False
- NextAction=StopBeforeArchiveOrResume

Optional Resume-entry *read-only* canary (does NOT inspect/resolve/move the transaction):

    .\OutlookPOP3Archive.ps1 -Mode Resume -ProfileName Outlook -Transaction 'c7e87652-e501-43ff-b622-5dcd87aee438' -Limit 1 -WhatIf -WorkerPilot -ConfirmDevWorkerPilot | Format-List

That ID is a synthetic prior LIVE4 run, but the pilot will NOT read its journal or invoke LIVE6.
An arbitrary nonzero GUID may be used instead because this milestone tests the dispatcher only.
No existing transaction is executed or modified.

## Stop conditions

Any gate rejection, abnormal worker outcome, timeout or missing/invalid response:
STOP, do not rerun on the same intended operation automatically and never fall through
to standard Archive/Resume. The canary itself is nonmutating Ping, so no journal Reconciled
resolution is needed for this read-only probe. Durable Intent, one-shot Move claims and
LIVE5/LIVE6 resolution will be required in a FUTURE mail-mutating Worker milestone;
they are not activated by the 2.6.5 canary.

No full backup LIVE2B, Inbox scanning, profile reconfiguration, Outlook.exe kill,
real Move, PST new creation, compaction, Resume operation, or production promotion.
