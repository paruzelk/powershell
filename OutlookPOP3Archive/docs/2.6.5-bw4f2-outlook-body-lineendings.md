# BW4f2 — narrow Outlook POP3 plain-text Body linebreak normalization

## Observed on real user test PST

BW4f1 Windows PowerShell 5.1 CI was 1721 PASS / 71 containers.
Original POP3 Inbox now has 26540 messages. BW4c selected the
correct TestId message using exact MAPI InternetMessageId Restrict,
zero full-folder enumerations; per-item identity and historical
one-Intent/seven SHA checks all passed.

The user then independently confirmed:
SubjectExact=True, BodyLength=250, HeaderMatches=0,
TestIdMatches=0, AttachmentCount=0.
The original typed Body has 237 characters under LF and 243
under CRLF. The extra seven characters are consistent with Outlook
adding extra carriage returns, but we cannot confirm the precise
line separator sequence until local testing.

## Code change

BW4f2 normalizes ONLY CR, CRLF, CRCRLF and mixed separator sequences
on an in-memory classifier string copy. It preserves the exact
original MailItem.Body and BW4c raw content SHA256 fingerprint,
received timestamp, SearchKey and MAPI identity. Exact Subject,
exact body marker, exactly one canonical TestId matching subject
GUID and explicitly proven zero attachments remain mandatory.
Customer messages, additional TestId, mismatches, attachments,
unknown Attachments collection, historical journal drift and
extra/forged worker-authorization fields continue to fail closed.

No Outlook MailItem.Move, PST edits, original historical journal
writes, Move retry, production Worker activation or stable FIX13b
changes are introduced.
