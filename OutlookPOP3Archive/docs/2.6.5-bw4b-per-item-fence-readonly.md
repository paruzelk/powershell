# 2.6.5-BW4b: per-item fence, Option B, read-only

BW4a was validated by native Windows PS5.1 CI (1572/63) and two real-host
read-only audits. BW4b preserves the historical BW3a journal with EXACTLY one
unresolved Intent, seven original evidence hashes and no resolution claims.

BW4b introduces pure per-item candidate classification using TWO independently
named read-only witness files and exact identity checks: SourcePst, SourceStoreId,
SourceEntryId, InternetMessageId, SearchKeySha256, ContentSha256, observed count=1.
Both captures must have distinct nonzero GUIDs, labels PrimaryReadOnly and
IndependentReadOnly, and all stable identity values matching. Candidate matches
to historical source/destination EntryID or InternetMessageId are BLOCKED,
including if just one witness matches. BW4a transaction/run and journal
checks are reused. Malformed, absent, inconsistent evidence FAILS CLOSED.

IMPORTANT: caller-provided JSON is not an independently authenticated MAPI
readback, even if values agree. A result of
PerItemEvidenceConsistentDesignOnlyNoWorkerDispatch is NOT permission to
execute the Worker. No production integration, no claim, no Move, no journal
write, no retry. All return flags for dispatch/write are false.
