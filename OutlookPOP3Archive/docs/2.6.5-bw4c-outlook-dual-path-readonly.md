# BW4c — Outlook/MAPI dual-read-path evidence, DEV only, Option B

## Scope

BW4b passed native Windows PowerShell 5.1 CI (1592 tests / 64 containers)
and the user confirmed the matching local CI result. BW4c adds one explicitly
opted-in **read-only COM attachment to an ALREADY RUNNING Outlook** plus
two separate read paths for the SAME selected POP3 MailItem:

1. Namespace.GetItemFromID(ItemEntryId, StoreId).
2. Namespace.GetFolderFromID(FolderEntryId, StoreId), followed by exact
   enumeration of Folder.Items.Item(i), with count bounded to <=MaxFolderItems.

The user supplies BOTH exact EntryIDs, plus the existing POP3 PST path and
Outlook profile. The script never guesses a candidate, creates an account,
starts Outlook, mounts/detaches a PST, writes a file, or calls MailItem.Move.
It requires exactly ONE mounted store whose FilePath is the selected local PST
and exactly ONE POP3 account whose DeliveryStore matches that store.
IMAP accounts never count as authorized POP3 delivery owners.

Pre-COM and post-COM Option-B BW4a audits require exact seven original
evidence SHA256s, exact one unresolved Intent, no historical resolution
claim, and the pinned BW3a journal SHA256. The historical SourceEntryId and
DestinationEntryId are **blocked before COM**; MAPI InternetMessageId and
both readbacks are checked through the BW4b per-item fence after COM.

Each reading generates an in-memory BW4b-compatible observation:
SourcePst, SourceStoreId, SourceEntryId, InternetMessageId (MAPI 0x1035001F),
SearchKeySha256 (MAPI PR_SEARCH_KEY, 0x300B0102), and a deterministic
subject/sender/body/size/received-time SHA256 with explicit length separators.
The raw body/subject/sender is never written to disk or returned in results.
The fingerprint is NOT full MAPI byte equality, does not prove attachment
equality, and is NOT a forensic stable byte hash of the PST.

## Critical trust boundary

Two access paths in ONE active Outlook session are **not independent external
evidence**: they may observe the same MAPI cache, and Outlook may update the
PST or metadata autonomously when it is open even though THIS script uses no
write API. It makes NO claim that PST bytes remain identical. The output
must always declare:
- IndependentlyAuthenticatedExternalEvidence=False
- FullMAPIContentByteEqualityVerified=False
- SourcePstUnmodifiedAtByteLevelProven=False
- WorkerDispatchAllowed=False
- OutlookMoveExecuted=False
- AutomaticRetryAllowed=False
- ProductionReady=False

Even on an exact dual-path identity match, NO synthetic or real Move permit,
no journal Reconciled, and no historical operation retry is authorized.
If the requested folder contains too many items, duplicate EntryIDs, an
unreadable message, multiple POP3 account owners or any mismatch, STOP without
claiming proof. A CI PASS is NOT a live-Outlook PASS.

## Opt-in on Windows PowerShell 5.1 STA

Run ONLY in a compatible running Outlook profile after selecting an
**unrelated, expendable synthetic test MailItem** and recording its exact
folder EntryID and MailItem EntryID through a separate read-only inspection.
Avoid the historical BW3a source or destination item. Do not run on a live
critical message as an implicit authorization to move it.

    $source = 'C:\Users\bogoderov_e\Documents\Файлы Outlook\info@stios.ru.pst'
    $folderEntryId = 'PASTE_SELECTED_SYNTHETIC_FOLDER_ENTRYID'
    $itemEntryId = 'PASTE_SELECTED_SYNTHETIC_MAILITEM_ENTRYID'

    .\OutlookPOP3Archive.ps1 -Mode Archive -ProfileName 'Outlook' -WhatIf -Limit 1 -WorkerPilot -ConfirmDevWorkerPilot -WorkerPilotReviewOutlookPerItem -WorkerPilotRunId 'a7b51427-7494-43f4-bc96-64915f6bee7e' -WorkerPilotSourcePst $source -WorkerPilotExpectedHistoricalJournalSha256 '5a68dbc4186c69eff13e49c7d69a19f16eba86e04969bb5aea3be0327820a648' -WorkerPilotCandidateFolderEntryId $folderEntryId -WorkerPilotCandidateEntryId $itemEntryId -WorkerPilotMaxFolderItems 1000 | Format-List

Or run standalone:

    .\Core\Diagnostics\Test-OPA265BW4cOutlookPerItemReadOnly.ps1 -RunId 'a7b51427-7494-43f4-bc96-64915f6bee7e' -SourcePst $source -ExpectedJournalSha256 '5a68dbc4186c69eff13e49c7d69a19f16eba86e04969bb5aea3be0327820a648' -Mode Archive -FolderEntryId $folderEntryId -CandidateEntryId $itemEntryId -ExpectedProfileName 'Outlook' -MaxFolderItems 1000 -Review -ConfirmExistingOutlookReadOnly | Format-List

For Resume also supply a DIFFERENT fresh nonhistorical transaction GUID
using -Transaction, or the BW4a preflight refuses it. Do NOT supply the
historic RunId as the transaction. If folder has more than 1000 items,
choose a smaller disposable test folder rather than overriding a safety
limit without review.
