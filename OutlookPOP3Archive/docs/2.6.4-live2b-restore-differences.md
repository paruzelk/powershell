# OutlookPOP3Archive 2.6.4-LIVE2B — explain one-folder restore mismatch

## Observed real Outlook result (LIVE2)

The user ran the one-shot LIVE2 restored-PST smoke test on an exact
TEMP copy of the validated existing POP3 backup:
- Original folder count: 9
- Clone folder count: 9
- FolderStructureAndCountsEqual: false
- DifferenceTypes: exactly one CountMismatch
- The clone was successfully detached; no mail was moved
- The original test PST and the reference backup were not modified
  by the diagnostic script.

This does NOT prove that the backup is corrupt. The original PST may
have changed after backup creation, or a special Outlook folder may
present a different count in the copied store. The previous report did
not capture the folder path and actual numeric pair; that omission
is the motivation for LIVE2B.

## New diagnostics

The PURE function Compare-OPA264RestoreFolderInventories now retains:
- FolderStructureEqual
- ItemCountsEqual
- SubfolderCountsEqual
- TotalItemsSource / TotalItemsRestored
- DifferenceCount
- Differences array with ONLY: RelativePath, Type, SourceItems,
  RestoredItems, SourceSubfolders, RestoredSubfolders.

The summary DifferenceTypes is retained for backward compatibility,
including CountMismatch for item or subfolder count differences.
No message subjects, sender addresses, identifiers, bodies, attachment
names or content are collected. A future real Outlook run still creates
a separate one-shot report, never a Completed/Reconciled journal entry.

Ten new synthetic offline Pester cases were added in the existing
Tests/Worker/ExistingPstRestoreProbe.Tests.ps1 container.
LIVE2B native Windows PS5.1 CI target: **500 tests / 36 containers**,
0 failed/0 skipped. This is a DEVELOPMENT snapshot: do not promote
to production Archive/Resume/Auto and do not enable normal Worker Move.

## Investigating the existing LIVE2 test

The previous RunId has been claimed/completed: NEVER run -ProbeClone
with it again or delete the claim. That old report cannot reconstruct
numeric counts because it did not persist them.

Run only the already-available read-only current POP3 diagnostic:

    $sourceReport = .\Core\Diagnostics\Test-OPA264ExistingPop3Pst.ps1 -PstPath $source -Review -MaxFolders 500
    $sourceReport.Folders | Sort-Object Items -Descending | Format-Table FolderPath,Items,Subfolders -AutoSize

The initial user-provided result had 26,310 Inbox items and the other
8 folders at zero. Treat this as an observation at that earlier time,
not as a guarantee for the backup or later current PST snapshot.

To obtain a future per-folder clone comparison, use a NEW RunId and
the LIVE2B package, run native CI first, and follow the existing
one-shot -Review, -PrepareClone and -ProbeClone steps. A new attempt
uses a fresh 7.2 GB temporary copy of the already preserved backup
and must confirm the current test PST/backup fingerprint and available
space. Never manually edit scope markers, requests or claim files.
If the original PST hash no longer equals the reference backup hash,
the existing cloning script intentionally fails closed. In that
case re-evaluate the source/backup snapshot relationship rather than
bypassing safety checks.

LIVE2B is NOT itself evidence that the original single CountMismatch
is resolved or that the backup is fully restorable.
