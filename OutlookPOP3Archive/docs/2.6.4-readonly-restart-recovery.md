## New modules

- Core/Worker/WorkerReadOnlyRecovery.ps1: reconstructs exact 2.6.4
  run-unique TEMP Source.pst/Archive.pst and source/destination identities
  from a persisted request, scope marker and SHA-checked append-only
  Intent. Accepts preexisting parent/worker one-shot claims for review;
  NEVER clears/reuses them. Validates request, optional barrier, claims,
  worker response and controller result; forged/corrupt evidence stops.
  Read-only result exposes classification and counts, no private message
  contents, no permission to retry, complete or mutate the journal.
- Core/Diagnostics/Invoke-OPA264ReadOnlyRecovery.ps1: a separate
  Windows PowerShell 5.1 STA process entrypoint requiring explicit
  -Review. Attaches only to already-running Outlook (GetActiveObject),
  verifies TWO existing mounted disposable StoreID/path identities,
  retrieves the exact two test folders, obtains complete source/target
  read-only snapshots, and outputs a limited JSON diagnostic result.
  Does not create, mount, detach or remove PST files; does not start
  workers, invoke Move, write journal terminal records or kill processes.
- Tests/Worker/WorkerReadOnlyRecovery.Tests.ps1: 23 synthetic non-COM
  tests, including one-shot claims, corrupt/missing evidence, duplicate
  snapshots, journal preservation and Unicode PST fixture format.

## Corrected prior fixture defect

The B2 fixture had incorrectly used AddStoreEx(..., 3) with the Unicode
comment. Microsoft OlStoreType defines olStoreUnicode=2 and olStoreANSI=3.
D changes BOTH disposable test fixture creation calls to 2 and adds a
regression test. These scripts are diagnostic only; production PST
creation and archive behavior remain unchanged.

Source of enum:
https://learn.microsoft.com/en-gb/office/vba/api/outlook.olstoretype

## Test process

1. Run native Windows PowerShell 5.1 Pester/PSScriptAnalyzer on exact D
   sources. Target 381 tests / 31 containers, zero failures or skipped.
2. Use ONLY a dedicated Outlook test profile/VM with TWO NEW PST files.
   Verify fixture output; no mailbox donor or user folders are involved.
3. For EACH controlled crash experiment, use a NEW RunId and disposable
   fixture. Preserve original journals, claim files and reports.
4. After the child/controller has exited, start an INDEPENDENT Windows
   PowerShell 5.1 STA process while only the two known test PSTs remain
   mounted, then run:

       powershell.exe -NoProfile -STA -File ".\Core\Diagnostics\Invoke-OPA264ReadOnlyRecovery.ps1" -RunId "<run-guid>" -Review

5. Inspect SourceMatches, DestinationMatches, ScanComplete, Status and
   claim/barrier presence. Never infer proof of successful Move from a
   unique destination fingerprint. Never repeat the same operation.
6. Archive/Resume/Auto stay on FIX13b; no production Worker routing.

## Strict limitations

No recovery result authorizes retry or a Completed/Reconciled journal
event. A missing response is not a failed Move. A read-only snapshot
after Outlook restart can have changed EntryIDs or StoreIDs, so
identity changes fail closed and are subject to phase E durability
tests. Crash barriers are correlation hints, not independently trusted
proof of prior process ownership. Mid-COM Move is not deterministically
injectable, and the C live crash experiments have not yet been run.

The project Core/Version.ps1 and RELEASE.json Build fields remain at
the 2.6.3-PREVIEW1 integration baseline; this ZIP is labeled 2.6.4-D
DEV only and must not be promoted to a release.
