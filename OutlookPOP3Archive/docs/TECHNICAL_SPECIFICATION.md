# Техническое задание OutlookPOP3Archive — требования к исходному коду

**Статус:** действующее дополнение к ТЗ проекта с 27.10.2026.
**Целевая среда:** Windows PowerShell 5.1 (Desktop), Outlook.
**Приоритет:** обязательное требование для всей дальнейшей разработки, включая DEV-ветки, hotfix, тесты и релизные пакеты.

## ТЗ-ENC-001. PowerShell-код — строго UTF-8 с BOM

1. **Все новые и любые изменённые PowerShell-файлы** (`.ps1`, `.psm1`, `.psd1`) сохранять **в UTF-8 с BOM**. Первые три байта файла обязательно должны быть `EF BB BF`. Правило распространяется на `Core/`, `Tests/`, точки входа и вспомогательные скрипты, даже если файл содержит только ASCII.
2. **Запрещено** создавать или сохранять изменяемый PowerShell-код в UTF-8 без BOM, ANSI/Windows-1251, OEM или UTF-16. Не допускать удаления BOM редактором, форматтером, Git-операцией, генератором, сборкой или при записи через API.
3. Причина: **Windows PowerShell 5.1** может интерпретировать `.ps1` без BOM по системной ANSI-кодовой странице. Кириллические литералы, пути к PST и другие Unicode-строки могут исказиться, что вызывает ложный отказ проверки идентичности или, в менее строгом коде, обращение к неверным данным. Ранее BW3b остановился на точном сравнении пути `SourcePst` по этой причине.
4. При создании/перезаписи кода через .NET использовать, например, `[System.Text.UTF8Encoding]::new($true)` и `[System.IO.File]::WriteAllText($path, $source, $encoding)`. Для Windows PowerShell 5.1 доступна также запись `Set-Content -Encoding UTF8`; после записи проверять **фактические байты** BOM, а не название кодировки.
5. Проверка приёмки **обязательна до запуска Pester и упаковки ZIP**: для всех PowerShell-файлов сверить три стартовых байта с `EF BB BF`. Технический переходный режим допускает только **82 ранее существовавших неизменённых файла без BOM** из исходного снимка BW3c. Любое изменение такого файла требует сначала сохранить его с BOM. Новые файлы без BOM недопустимы.
6. Переходный снимок — SHA-256 отсортированного списка `relative/path<TAB>sha256-of-file` (разделитель строк LF, без завершающего LF) всех ранее существовавших файлов без BOM:
   `ace042f4ab915f2c1bd274685ea0e041e1f94f05c82418bed5a893ae153967ca` (82 файла).
   Любое изменение набора или байтов этих файлов требует **отдельно рассмотренной миграции**: перевода соответствующего файла в UTF-8 BOM и обновления переходного снимка. Нельзя добавлять новые или изменённые файлы в исключения только ради прохождения CI.
7. `.editorconfig` проекта устанавливает `charset = utf-8-bom` для PowerShell-файлов. CI/Pester проверяют фактические байты независимо от настроек редактора.
8. Это требование **только к исходному PowerShell-коду**. JSON, JSONL-журналы, worker request/response, электронные письма, бинарные PST и другие протокольные/данные файлы должны сохранять свой утверждённый формат; **нельзя** автоматически добавлять BOM к журналам или JSON, поскольку это может повредить формат или контрольные суммы.

## ТЗ-SAFE-001. Независимые ограничения безопасности остаются неизменными

- Production FIX13b не меняется вследствие требований к кодировке; `ProductionReady=False`, production `RealMailMoveViaWorker=False`.
- Никакого автоматического повтора `MailItem.Move` после любой попытки/сбоя/тайм-аута или существующего долговечного dispatch/attempt claim.
- Любой аудит предыдущих синтетических операций выполняется read-only, без изменений PST, журнала, исходного `Intent` или claims.
- Изменение кодировки исходников **не является разрешением** на новую синтетическую или production-операцию Move.

## Критерий приёмки

Изменение кода принимается только если исходный текст PowerShell сохранён в UTF-8 BOM, тест кодировки и прочие локальные и Windows PowerShell 5.1 CI-gates проходят без ошибок, а DEV/production-ограничения сохраняются. Для исторических BOM-less файлов действует исключительно фиксированный неизменный переходный снимок.
