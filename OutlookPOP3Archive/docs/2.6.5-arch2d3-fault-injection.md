# ARCH2d3 — испытания отказов и аварийных окон пакета из 10 писем

**Режим:** только синтетический Windows PowerShell 5.1 GitHub Actions. Предыдущий реальный ARCH2d `RunId=23ee0a5b-4780-45a2-9ef6-e12992b418f4` завершился `AllTenIndependentPostRestartSemanticMatches` (`10/10`, включая письма с поддерживаемыми вложениями). Его исходный PST, архив и immutable журналы ARCH2c4a/ARCH2d здесь **не читаются и не изменяются**.

## Что нового

`Core/Diagnostics/ARCH2d3FaultSimulator.ps1` воспроизводит полную модель **10 последовательных операций** в изолированном синтетическом каталоге. Для глобальной заявки, индивидуальных заявок и записей возврата используется именно production-функция `Write-OPA265ARCH2c4JsonOnce` — `FileMode.CreateNew`, force-flush записи, SHA-256. Состояния исходных MailItems и назначения имитируются объектами PowerShell, **ни один реальный Outlook COM не подключается, физические PST не создаются и не читаются**.

Матрица 19 типов сценариев × три точки отказа (1-е, 5-е, 10-е письмо) = **57 случаев**:

1. `None`: эталонные десять успешных операций.
2. `GlobalClaimCollision`: файл глобальной заявки уже существует.
3. `GlobalClaimTornWrite`: частично записанная глобальная заявка.
4. `AfterGlobalClaimBeforeFirstItem`: прерывание после глобальной заявки до первого письма.
5. `ItemClaimCollision`: конфликт индивидуального журнала.
6. `ItemClaimTornWrite`: частично записанный индивидуальный журнал.
7. `AfterItemClaimBeforeCom`: прерывание после force-flush заявки до COM.
8. `ComThrowsWithoutApply`: COM отказал до перемещения (модель).
9. `ComAppliesThenThrows`: COM переместил письмо и затем вернул ошибку (модель).
10. `ComReturnsBeforeReceipt`: перенос состоялся, но запись результата не успела сохраниться.
11. `ReturnReceiptCollision`: конфликт записи результата.
12. `ReturnReceiptTornWrite`: частичная запись результата.
13. `AfterReturnCrash`: аварийная остановка после успешной записи результата.
14. `ChangedOriginalBeforeGlobalClaim`: несовпадение источника до глобальной заявки.
15. `ChangedOriginalBeforeItemClaim`: изменение письма после общей заявки, но до заявки письма.
16. `ChangedDestinationBody`: несоответствие SHA-256 Body после переноса.
17. `UnknownSourceProvider`: провайдер не подтверждает исходное состояние EntryId.
18. `DuplicateDestination`: лишний элемент назначения.
19. `NoRestart`: независимая проверка до подтверждённого перезапуска Outlook.

В каждом сценарии контролируются сохранённые заявки, отсутствие скрытого `continue`, количество имитируемых COM вызовов и полный семантический статус на основании оригинального `Get-OPA265ARCH2dReconcileDecision`. **Ни один отказ не выдаёт разрешение автоматически повторять `MoveBatch`, менять старые заявки или включать `Archive/Resume/Auto`.**

## Важные различия и ограничения

- Если COM **изменил** состояние, а затем выдал исключение, отсутствие `move-XX-return.json` не является доказательством неудачного Move. Выполнять повторный Move запрещено.
- Если журнал заявления повреждён, возвращается **ручная проверка**, а не новый запуск.
- Полностью достоверная после рестарта партия может быть проверена даже если процесс упал сразу после десятой сохранённой записи возврата: **проверка не означает разрешения переписать/повторить заявки**.
- Если записанная заявка свидетельствует о намерении, но письмо осталось в источнике, это **не разрешает повторный перенос**.
- Модель не доказывает реальную транзакционность Outlook PST, физическую устойчивость к power loss, корректную интерпретацию неопределённых MAPI-флагов и безопасность 90 ГБ при массовом режиме. Для этих проверок нужен отдельный этап ARCH2d4 и реальные fault injection в изолированной лаборатории. В текущей сборке эти возможности **не включены**.
- Схематическая модель `ReturnReceipt*` классифицирует повреждённые квитанции как требующие ручной проверки. Это усиленный критерий симулятора; фактическое архивирование не объявляется проверенным на всех таких состояниях.

## Команды

Новый операторский `Invoke-ARCH2d3.ps1` **по умолчанию делает только `Plan`** и не касается Outlook/PST:

```powershell
.\Invoke-ARCH2d3.ps1 -Mode Plan | Format-List
```

Запись 57 синтетических сценариев в **отдельный** scratch-каталог (не `Файлы Outlook`, не `%LOCALAPPDATA%\OutlookPOP3Archive-ARCH2d-RealBatch10`) — только если нужен локальный дубль CI:

```powershell
$scratch=Join-Path $env:TEMP ('OPA-ARCH2d3-SYNTH-'+[guid]::NewGuid().ToString('N'))
[void][IO.Directory]::CreateDirectory($scratch)
$result=.\Invoke-ARCH2d3.ps1 -Mode Simulate -SandboxRoot $scratch
$result | Format-List Schema,Status,Cases,InjectedFaultCases,AutomaticRetryAllowed,ProductionReady
$result.ResultRows | Select-Object Fault,FaultAt,GlobalClaimValid,IndividualClaims,FakeComMoveCalls,VerifiedMoved,ReconcileStatus,ReplayBlocked | Format-Table -AutoSize
```

Симулятор оставляет свои временные JSON-доказательства в `$scratch`; это намеренно отдельный каталог. Никакой связки с реальными архивными PST в этих командах нет. Для обычного приёмочного теста достаточно GitHub Actions; ничего запускать на рабочем Outlook не требуется.

## Требования перед ARCH2d4

1. Гарантированная read-only классификация любого частично завершённого набора из десяти исходных писем, включая недостоверную заявку.
2. Запрет на retry даже после исключения COM, если неизвестно, применился Move или нет.
3. Различение полной семантической сохранности и отсутствующей/неверной квитанции.
4. Нельзя присвоить результату crash-модели статус *real-world crash consistency* без реальных стендовых испытаний.
5. Перенос 100 реальных писем только после согласованной и проверенной процедуры независимого восстановления после частичного выполнения.

## Релизная верификация

Windows PowerShell 5.1, PSScriptAnalyzer, UTF-8 BOM для новых PowerShell-файлов, полный Pester и JSON build-gates, ZIP только `OutlookPOP3Archive`, SHA-256 архива и неизменяемая GitHub точка отката. Переход из DEV в производство и общие `Archive/Resume/Auto` остаются заблокированы.
