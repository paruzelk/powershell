  - Standalone, explicit -Review, Windows PowerShell 5.1 STA read-only

    established 2.6.4-D recovery entrypoint for independent COM scans

## Diagnostic-only example

Run the project-local Invoke-CI.ps1 first under Windows PowerShell 5.1:

    .\Invoke-CI.ps1 -ExpectedBuild '2.6.3-PREVIEW1'

Expected: 442 tests / 33 containers, zero failures/skipped.

On an ISOLATED TEST Windows machine with a previously approved,
disposable and already mounted pair of Outlook PST files and one
RunId-specific journal, start a FRESH Windows PowerShell 5.1 STA
process and call:

    powershell.exe -NoProfile -STA -File ".\Core\Diagnostics\Invoke-OPA264EvidenceAudit.ps1" -RunId "<RUN-GUID>" -Review -ExpectedCrashWindow "WorkerStartedBeforeMove"

The command emits a sanitized JSON object only. If an expected crash
barrier is missing or different, classification becomes EvidenceConflict.
If a destination candidate matches, classification is CandidateObserved,
NEVER ProvenMoved. If identity differs, classification is IdentityChanged
and the old durable Intent MUST NOT be modified.

Do not attempt another Move for the same RunId, remove claims, delete
evidence, mark a journal Completed/Reconciled, or run this against a
normal mailbox/RDS production user profile. Read-only review does not
itself require PST detach/reopen.

## Important semantics

- Status is a diagnosis of OBSERVED evidence; it does not claim that
  the source or destination PST is crash-consistent or uniquely owned.
- SourceOnly never means it is safe to retry. DestinationCandidate
  never proves that the original message was moved successfully.
- Missing/partial/corrupt evidence is blocked, not silently ignored.
- A synthetic CI report is not proof of an Outlook COM integration test.
- Report schema omits Sender, Subject, InternetMessageId, EntryIDs and
  message bodies. The observed RunId and OperationId remain available
  for correlation.
- ProductionReady is ALWAYS false; AutomaticRetryAllowed,
  AutomaticCompletionAllowed, MailMoveAllowed, JournalWriteAllowed and
  IndependentMoveProof are ALWAYS false for these diagnostic reports.
- A deterministic barrier cannot be placed inside the synchronous
  Outlook MailItem.Move call, so the DuringMove case remains a separate
  non-deterministic test/reconciliation concern.
