# ARCH3c — защищённые файловые квитанции + исходный OperationJournal (синтетика)

**DEV. Это не рабочий массовый перенос почты.** Этап интегрирует в синтетическом режиме реальные механизмы дисковой записи доказательств и **существующий** `Core/Archive/OperationJournal.ps1`. Исходный `OutlookPOP3Archive.ps1`, `MailMover.ps1`, `ArchiveTransaction.ps1`, `ArchivePlanner.ps1`, `ArchiveVerifier.ps1`, `DuplicateIndex.ps1` остаются неизменными; `Archive`, `Resume`, `Auto` заблокированы.

Архитектура: [ADR ARCH3-001](ADR-ARCH3-001-reuse-existing-archiver.md), [ARCH3a](2.6.5-arch3a-existing-pipeline-audit.md), [ARCH3b](2.6.5-arch3b-original-mover-contract.md).

## Что уже реально сохраняется на диск

`Core/Archive/ARCH3cDurableOperationLedger.ps1` принимает **тот же** `ARCH3b.OperationContract` с годом, PST, StoreID, EntryID, TransactionId, исходной и архивной папками. Для защиты от изменения пользовательских PST этот этап **работает только в OS TEMP и только при `TransactionId`, начинающемся с `ARCH3C-SYNTHETIC-`**.

Пишутся файлы (по одному, `FileMode.CreateNew` + `Flush(true)`, никогда не перезаписываются):

| Порядок | Файл | Содержание |
| --- | --- | --- |
| 1 | `PrepareIntent.json` | Идентификатор исходной операции ДО потенциального создания архива |
| 2 | `DestinationReady.json` | **Только модель** готовности назначения; реальный PST не открывается |
| 3 | `SourceWitnessAnchored.json` | **Синтетический** контрольный SHA, не хеш настоящего письма |
| 4 | `MoveClaimed.json` | Имитация durable заявки ДО возможного COM Move |
| 5 | `MoveReturned.json` | Имитация полученного Destination EntryID |
| 6 | `IndependentContentVerified.json` | Имитация проверки, **не подтверждение реального перезапуска Outlook** |
| 7 | `IndexCommitted.json` | Имитация допуска записи индекса, **настоящий DuplicateIndex не меняется** |
| Итог | `final-seal.json` | SHA256 всех семи файлов + SHA256 оригинального OperationJournal |

Каждая стадия содержит `PreviousStageSha256`, `OperationId` и `ContractSha256`. Последняя `FinalSealSha256` выдаётся оператору и передаётся отдельно для read-only `Evidence`. Изменение любого файла или `OperationJournal` приводит к отказу подтверждения цепочки. Даже успешный `Evidence` имеет статус `SyntheticDurableStageAndOriginalJournalChainFullyPinnedNoOutlook` и **не разрешает production**.

**Используется оригинальный `Write-OPAOperationJournalEvent`**, а для проверки — оригинальные `Read-OPAOperationJournal` и `Resolve-OPAOperationRecovery`. Журнал получает `Intent` и затем `Reconciled` только для **синтетической** операции под отдельным маркером и в отдельном TEMP-каталоге. Существующий `Resolve-OPAOperationRecovery` считает `Completed` терминальным и не позволяет `Reconciled` после него; этот контракт выявлен при интеграции и требует отдельного проектирования для реального пути `Move`. Не следует исправлять это слепым изменением оригинального журнала.

**При аварии:** файлы остаются неизменёнными, повторное выполнение того же синтетического запуска запрещено. Если `MoveClaimed.json` есть, а `MoveReturned.json` отсутствует, это классифицируется как неопределённый исход. Не использовать такие доказательства для настоящего Move/Resume. Ни одна операция ARCH3c не перемещает/удаляет письма и не подтверждает фактическую целостность PST.

## Проверка в Windows PowerShell 5.1

```powershell
.\Invoke-ARCH3c.ps1 -Mode Plan | Format-List

$source='C:\Users\bogoderov_e\Documents\Файлы Outlook\info@stios.ru.pst'

# WhatIf: нет даже синтетической записи
.\Invoke-ARCH3c.ps1 -Mode SyntheticWrite -SourcePst $source -WhatIf | Format-List

# Опционально: реальная запись ТОЛЬКО СИНТЕТИЧЕСКИХ JSON в OS TEMP
$synthetic=.\Invoke-ARCH3c.ps1 -Mode SyntheticWrite -SourcePst $source -ConfirmSyntheticWrite -Confirm:$false
$synthetic | Format-List

# Повторно выполнять SyntheticWrite для того же каталога нельзя
$tx=Split-Path -Leaf $synthetic.EvidenceRoot
$review=.\Invoke-ARCH3c.ps1 -Mode Evidence -SourcePst $source -TransactionId $tx -ScratchRoot $synthetic.EvidenceRoot -FinalSealSha256 $synthetic.FinalSealSha256
$review | Format-List
```

Путь `SourcePst` используется только для вычисления существующего архивного имени. **Файл PST не открывается и не создаётся.** Команда `SyntheticWrite` создаёт до девяти небольших JSON/JSONL-файлов в `$env:TEMP`, включая `OperationJournal` и финальную печать.

Ожидаемые результаты:
- `Plan.Status = SyntheticOnlyOriginalOperationJournalAdapterPlanNoPstNoComNoFiles`;
- `SyntheticWrite.Status = SevenDurableSyntheticStagesAndOriginalOperationJournalSealedNoCom`;
- `Evidence.Status = SyntheticDurableStageAndOriginalJournalChainFullyPinnedNoOutlook`, `StageCount=7`, `OriginalOperationJournalEventCount=2`, `FinalSealExternallyPinned=True`, `Issues={}`, `ProductionReady=False`.

Если произойдёт ошибка — сохранить временные JSON/JSONL для разбора, **не перезаписывать**. Для проверки отключений есть `-InjectStopAfter MoveClaimed`; используйте лишь на новой синтетической партии в TEMP. Не использовать этот аргумент в рабочих сценариях.

## Реальные пробелы перед безопасным старым архиватором

1. Сохранить оригинальный алгоритм выбора PST/Year/Sent и рекурсивный обход папок без дублирования.
2. Подключить подготовительный **реальный**, внешний и durable intent **перед `Get-OPAArchiveDestination`** в legacy `MailMover`.
3. Привязать оригинальную транзакцию, её step journal, `OperationJournal`, независимые индивидуальные claims/receipts и архивный `DuplicateIndex` к единому `OperationId` / SHA.
4. Не считать legacy `Completed` доказанным `Reconciled`: необходимо подтвердить полный оригинальный semantic witness после отдельного процесса Outlook, до финального статуса.
5. Обеспечить восстановление **только по независимо проверенным результатам** и запрет на replay неопределённого COM Move.
6. Провести реальные изолированные испытания Year/Sent/custom folder, нескольких PST и аварий, затем нагрузочное испытание на 90 ГБ.

ARCH3c подтверждает **устойчивость файловых доказательств на синтетике**, но не завершает настоящую интеграцию массового `MailMover` и не даёт `WriterPermit`.
