## How actual verified-copy rehearsal works

1. Require Windows PowerShell 5.1 STA, exact RunId/PST/hash and
   explicit -RehearseVerifiedCopy.
2. Rerun BW3j -Review (full independent Outlook and claims evidence);
   validate its entire 42-field evidence verdict, including explicit
   no-write/no-production flags.
3. Read original seven file SHA256s and one original Intent, verify
   the pinned byte hash, original request and open original journal
   for READ only, never a write handle.
4. Create a fresh OS TEMP copy sandbox with one GUID. FileMode.CreateNew
   copies the exact original bytes into
   copied-original-intent.operations.jsonl; write a COPY ONLY marker.
5. Accept only that sandbox path for the rehearsal writer. Create
   one-shot bw3l-copy-resolution.claim via CreateNew/Flush(true),
   exclusively lock COPY journal, re-read byte SHA256 under lock,
   append hashed JSONL Reconciled sequence 2, Flush(true).
6. Journal replay on COPY must have exactly Intent + Reconciled and
   zero pending. Re-running any used sandbox, including partially
   written claim or torn append, must STOP unconditionally.
7. Recheck seven ORIGINAL hashes, original one-event journal unchanged
   and absence of original legacy/future resolution claims. Return
   explicit original untouched / copy Reconciled status.

Offline Pester does NOT use any actual original journal, PST or
Outlook. It generates a distinct historical-SHAPED synthetic Intent
with same RunId/OperationId but DIFFERENT SHA256, and marks that mode
OfflineReplicaNotHistoricalProof. The replica cannot masquerade as
ActualHistoricalByteCopy. It tests claim crash gaps AfterClaim,
PartialAppend and AfterAppend, altered marker, altered bytes,
partial claim, exclusive lock, path traversal, forbidden real path,
source seed unchanged, and no Archive/Resume/Auto integration.

## Write-authorization boundary and technical limitations

BW3l deliberately contains only a COPY writer. Positive BW3l is NOT
approval to modify the original journal. A future original
historical-run writer requires an independent security and
consistency review, explicit consent for precisely one RunId,
OperationId and Reconciled event, and separate operational gates.
The BW3g1 +8-byte size acceptance is NOT journal approval.

Exclusive file lock and Flush(true) mitigate, but cannot eliminate
all power-loss/storage crashes, path-based race conditions or
malicious concurrent file replacement. Claim + journal are two
separate durable records; after claim-before-append or
append-before-verify crash, manual investigation is required.
No automatic retry, no production promotion, no PST mutation.
FIX13b remains immutable and worker production flags are false.
