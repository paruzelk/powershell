# ARCH2c2 — приватный TEMP, эксклюзивная lease и модель остатков после аварии

**Версия:** `2.6.5-ARCH2c2` DEV. **Предыдущее состояние:** `ARCH2c1`, коммит `3efa6d3be9005edc88c240b6de2ace66f375fd15` (3764/126 CI PASS).
**Ограничение:** `Archive`, `Resume`, `Auto` остаются **заблокированы** защитой ARCH2a; ни один тест этапа не подключается к реальному Outlook или PST.

## Что сделано

- Новый `Core/Archive/ARCH2c2TempSafety.ps1` поддерживает только Windows PowerShell 5.1 / NTFS; отдельная рабочая директория `OPA-ARCH2c1-<guid>` создаётся с **заданным на момент создания защищённым DACL** (владелец — текущий Windows SID, полные права только у этого SID и LOCAL SYSTEM). Наследование выключено. Нет временного окна, в котором директория сначала наследует широкие права, а потом исправляет ACL.
- Права читаются и повторно проверяются до обработки вложений и перед очисткой. Любой неожиданный SID, запрещающий ACE, наследование, неподходящий владелец или reparse point ведёт к **STOP**. Поддержка FAT, UNC и нестандартного устройства с неработающим ACL не заявлена.
- Создаётся файл `.opa-lease` через `FileMode.CreateNew`, открытый с `FileShare.None`. Дескриптор остаётся открытым во время `Attachment.SaveAsFile`, SHA-256 и удаления файла вложения. Стандартное завершение закрывает lease, удаляет её файл и выполняет **только нерекурсивное** удаление пустой директории.
- После жёсткого завершения процесса .NET автоматически освобождает дескриптор, но `.opa-lease` и копия вложения могут остаться. Существующая `Get-OPA265ARCH2c1AttachmentWorkspaceInventory` теперь **только наблюдает** статус `LeaseState`: `HeldOrUnavailable`, `NotHeldAtObservation`, `Absent`, `UnsafeReparsePoint`. **Ни один статус не разрешает автоматическое удаление**: моментальное наблюдение не исключает гонку и работающий другой процесс.
- Файловый `MailItem.Size`, сырые байты Body, названия исходных вложений и ключи доступа не записываются в `.opa-lease`. Копии содержимого вложений до штатного удаления всё ещё содержат реальные байты и должны считаться конфиденциальными.

## Проверка read-only

```powershell
# В каталоге OutlookPOP3Archive; не присоединяет PST и не двигает письма.
. .\Core\Archive\ARCH2bSemanticWitness.ps1
Get-OPA265ARCH2c1AttachmentWorkspaceInventory |
    Select-Object WorkspacePath, LeaseState, RequiresManualReview, AutomaticallyDeleted |
    Format-Table -AutoSize
```

Не путать `NotHeldAtObservation` с разрешением на удаление. Для ручной очистки сначала закрыть все архиваторы, доказать принадлежность только этому инструменту и проверить отсутствие работающих lease / критического evidence. Автоматической команды удаления проект **не** предоставляет.

## Проверки

`Tests/Archive/ARCH2c2TempSafety.Tests.ps1`: 14 синтетических тестов NTFS-DACL (protected, current user, SYSTEM), исключительного доступа к lease, безопасного удаления, отказа при постороннем файле, отсутствующего каталога, унаследованного ACL, фиктивного аварийного закрытия дескриптора, read-only инвентаризации и сохранения запрета основных writer modes. Старые 3764 теста тоже должны пройти. Целевое значение: **3778 Pester / 127 test containers**, 0 errors/skips. Рабочие письма в CI не создаются и не перемещаются.

Это **не** настоящий процессный `kill`, ОС crash/отключение питания, тест с реальным Outlook COM `SaveAsFile`, доказательство `Copy -> Verify -> Delete`, и не приёмка 90 ГБ PST. Всё это остаётся входом в следующий ограниченный интеграционный этап, после дополнительного review несоответствий COM.

## Закреплённые условия

- Только чистый PowerShell 5.1 и стандартный .NET Framework, без внешних библиотек и заимствования стороннего кода.
- Любые новые и изменённые `.ps1` строго UTF-8 BOM (`EF BB BF`).
- Полные CI-gates: Windows PowerShell 5.1, PSScriptAnalyzer, Pester, JSON, исторические тесты, только проектный ZIP и SHA-256.
- Для всех `Indeterminate` исходный `Move Started` запрещает слепой `Resume`. Ни один обход защиты или автоматическое удаление писем не разрешены.

Следующий инженерный шаг — **ARCH2c3**: интеграционная disposable-PST проверка работы нового temp ACL/lease через реальный Outlook COM и отдельно запланированная транзакционная модель `Copy → Verify → Delete` с самостоятельным журналом (не равнять её с атомарным COM Move).
