# BW3k: isolated synthetic journal append and crash-gap test

## Scope and evidence

Historical BW3j native PowerShell 5.1 local CI (1301 / 59) and real
Outlook READ-ONLY audit PASSED. Existing historical BW3a one-Intent
journal, seven hashes, PSTs and consent file remain immutable.

BW3k is NOT authorization to reconcile historical BW3a. It creates
fresh TEST-ONLY synthetic journals under OS TEMP in directories named
OPA-BW3k-Sandbox-{32hex}, each with NEW random RunId/OperationId and
fake archive EntryID, source EntryID, and fake archive path
BW3K-SANDBOX-NO-PST. NO PST is created, copied, mounted or modified.
NO Outlook COM or Worker Move.

An isolated test marker pins the fresh journal SHA256 and exact marker
schema, rejects any original BW3a RunId/OperationId/journal SHA256,
historical PST path, production or operator consent flag. The writer
refuses any directory outside direct child of OS TEMP, partial claim,
symlink/reparse marker/journal, changed hash, extra/missing event or
other non-synthetic fixture.

## Journal protocol in fresh temp fixture ONLY

1. Create a new, random sandbox directory and write exactly ONE
   synthetic Intent event using the existing hashed JSONL journal code.
2. Persist a test-only marker via CreateNew, Flush(true).
3. Verify marker, exact one original Intent and original SHA256.
4. Persist a durable one-shot resolution claim via CreateNew,
   FileShare.None and Flush(true). Existing claim blocks forever;
   never automatically retry.
5. Hold an exclusive FileStream lock, re-read exact journal bytes and
   reverify the original SHA256 and all original Intent fields.
6. Append one synthetic Reconciled event (Sequence 2), Flush(true).
7. Validate existing Read-OPAOperationJournal and
   Resolve-OPAOperationRecovery: one resolved, zero indeterminate.
8. Return the fresh sandbox original/final SHA256. The original BW3a
   Intent, PSTs, claims and approval JSON are never touched.

## Failure and negative tests

- AfterClaim: durable claim exists, original journal unchanged;
  further attempt blocked.
- PartialAppend: deliberately torn journal tail retained and flushed;
  claim exists; never repair or retry.
- AfterAppend: flushed terminal event retained; verification gap
  simulated; claim blocks all subsequent writes.
- Existing/partial claim: hard STOP without modifications.
- Held external journal lock: no append without exclusive access.
- Added journal line, terminal record, torn Intent, mutated bytes,
  tampered marker, historical identifiers or real PST: STOP.
- No production integration and no authorization granted.

Pester removes only its own freshly generated sandbox fixture
directories. The optional -SelfTest retains its independent fresh
sandbox directory for operator inspection; no path or RunId input is
accepted by the self-test entrypoint.

## Limitations and future authorization boundary

Claims and journal form two separate durable files, NOT an atomic
transaction. Crashes after claim/before append or after append/before
verification must require manual review, NEVER an automatic retry.
Flush(true) cannot mathematically eliminate all underlying storage
failure scenarios. In addition, only a synthetic journal has been
tested, not a real Inbox or PST.

BW3k does not provide any historical production writer, does not
implement a separate explicit operator authorization workflow, and
does not prove byte-for-byte historical MAPI content preservation.
The accepted +8-byte variance applies only to one synthetic message,
and is NOT approval to Reconciled.

After local sandbox tests, a separate history-scoped writer design,
security review and NEW explicit one-run authorization are required
before any write to the historical evidence. FIX13b remains frozen;
ProductionReady=False; RealMailMoveViaWorker=False.
