# BW4k7v2a8 — read-only forensic of HASATTACH and +124-byte size drift after real one-shot Move

## Real operator evidence (2026-11-11)

The **one and only** Outlook `MailItem.Move()` from BW4k7v2a7 returned successfully and was independently reconciled after restarting Outlook. Exact original disposable test SuiteId `1a6683eb-3136-46eb-a1a8-ed8ece33b52c`. Original manifest SHA256 `77311b1df742545e15c01d755858b31395e76446fd4d43497775b2bed98bc2f1`; original one-shot claim SHA256 `ff4093e90fb7663d514085f087ea2cd46fde6c7c6bdb23b36f38ba41c1aa21a2`; original Move return observation SHA256 `9a89be00eeb85163afd557494bf16b7999c45f388fd7a25c59c35ccc65bf62cc`; destination EntryId `00000000D2D5FCF473B27142BB218ABB3C07996824002000`.

Original source exactly **0**, target exactly **1**, Outlook restart proven, saved pre-Move semantic SHA matched destination (subject/body/To/Unread/Class). Outlook message `Size` changed **1952 → 2076 bytes (delta +124 bytes)**, and raw `PR_MESSAGE_FLAGS` changed **9 (`0x09`) → 25 (`0x19`)**.

Bitmask XOR is **16 (`0x10`)**, which is `MSGFLAG_HASATTACH`. `MSGFLAG_READ` and `MSGFLAG_UNSENT` were present before and after. This is precisely defined by Microsoft [PidTagMessageFlags](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagmessageflags-canonical-property) and [PidTagHasAttachments](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtaghasattachments-canonical-property). `PR_HASATTACH` is computed by the message store from the flag, so an equal pair of `PR_HASATTACH=True` and `MSGFLAG_HASATTACH=True` is not independent proof of the existence of a *real* file attachment.

Microsoft's [MailItem.Size](https://learn.microsoft.com/en-us/office/vba/api/outlook.mailitem.size) returns only total item size in bytes. The +124 bytes cannot be reliably attributed to attachment data, headers, or MAPI provider state without a source/destination property-level inventory. **Original source `Attachments.Count` was not independently captured before the Move.** This stage must not invent it from the synthetic fixture creation code.

The first failed `Reconcile` run was due to the operator closing Outlook but running Reconcile *before opening Outlook again*; a later Reconcile after Outlook restart succeeded. No Move retry occurred.
