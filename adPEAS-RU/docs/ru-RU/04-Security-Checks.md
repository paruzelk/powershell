# <a id="security-checks-reference"></a>Справочник проверок безопасности

Полный справочник проверок безопасности, выполняемых adPEAS v2.

---

## <a id="output-filtering-noise-reduction"></a>Фильтрация результатов (снижение шума)

Некоторые проверки исключают из результатов высокопривилегированные учётные записи, чтобы уменьшить шум и выделить находки, требующие действий. Это сделано намеренно: ожидается, что Domain Admins и Enterprise Admins имеют права DCSync, GenericAll или сброса пароля. Их включение скрыло бы действительно нетипичные разрешения.

### <a id="filtered-checks"></a>Проверки с фильтрацией

В следующих проверках высокопривилегированные учётные записи по умолчанию отфильтровываются:

| Проверка | Что исключается | Параметр отмены фильтра |
|-------|-----------------|-------------------|
| **Get-DangerousACLs** | Domain Admins, Enterprise Admins и SYSTEM с правами GenericAll/WriteDACL/WriteOwner/DCSync | `-IncludePrivileged` |
| **Get-PrivilegedGroupMembers** | Анализ ACL AdminSDHolder исключает ожидаемых привилегированных субъектов | `-IncludePrivileged` |
| **Get-PasswordResetRights** | Выводятся только находки Critical/High; привилегированные учётные записи с правом сброса имеют низкую серьёзность | `-IncludePrivileged` |
| **Get-LAPSPermissions** | Только серьёзности Critical/High/Medium; чтение LAPS группой Domain Admins ожидаемо | `-IncludePrivileged` |
| **Get-GPOPermissions** | Group Policy Creator Owners и Domain Admins с правами изменения GPO | `-IncludePrivileged` |
| **Get-ADCSVulnerabilities** | Domain Admins и Enterprise Admins с правом регистрации сертификатов | `-IncludePrivileged` |
| **Get-AddComputerRights** | Domain Admins и Account Operators с правом создания компьютеров | `-IncludePrivileged` |
| **Get-BitLockerRecoveryKeyAccess** | Привилегированные субъекты с делегированным чтением паролей восстановления — Domain Admins читают их по умолчанию | `-IncludePrivileged` |
| **Get-DeletedObjectAccess** | Субъекты Tier 0 и служебные группы Exchange с правом просмотра Deleted Objects: Administrators может иметь его по умолчанию, установка Exchange выдаёт его | `-IncludePrivileged` |

### <a id="how-filtering-works"></a>Как работает фильтрация

adPEAS использует **классификацию по SID**, независимую от языка ОС (работает на английской, немецкой, французской и других локализациях):

1. **Test-IsPrivileged**: распределяет субъекты по категориям:
   - `Privileged`: Domain Admins (-512), Enterprise Admins (-519), Schema Admins (-518), Administrators (S-1-5-32-544), SYSTEM (S-1-5-18)
   - `Operator`: Account Operators, Server Operators, Backup Operators, Print Operators.
   - `BroadGroup`: Everyone, Authenticated Users, Domain Users.
   - `Standard`: обычные пользователи и группы.

2. **Test-IsExpectedInScope**: применяет фильтрацию с учётом контекста конкретной проверки:
   - Возвращает `Expected` для субъектов, которым право положено (исключаются из результатов).
   - Возвращает `Attention` для формально ожидаемых, но значимых для безопасности субъектов (жёлтая подсветка при `-IncludePrivileged`).
   - Возвращает `Finding` для субъектов, которым такого права быть НЕ должно (показываются всегда).

### <a id="viewing-all-results"></a>Как увидеть все результаты

Для отображения всех результатов, включая привилегированные учётные записи, используйте `-IncludePrivileged`:

```powershell
# По умолчанию: только неожиданные/опасные находки
Get-DangerousACLs

# Все находки, включая Domain Admins и Enterprise Admins (жёлтая подсветка)
Get-DangerousACLs -IncludePrivileged
```

### <a id="checks-without-filtering"></a>Проверки без фильтрации

Следующие проверки намеренно показывают ВСЕ учётные записи независимо от уровня привилегий:

- **Get-KerberoastableAccounts** — Kerberoasting возможен и для административных учётных записей.
- **Get-ASREPRoastableAccounts** — отсутствие предварительной аутентификации опасно для любой записи.
- **Get-UnconstrainedDelegation** — неограниченное делегирование опасно независимо от типа записи.
- **Get-ConstrainedDelegation** — отображает все конфигурации делегирования.
- **Get-InactiveAdminAccounts** — цель проверки: найти неактивные административные записи.
- **Get-AdminPasswordNeverExpires** — цель проверки: найти административные записи с бессрочным паролем.

### <a id="admin-only-checks-admincount1"></a>Проверки только администраторов (adminCount=1)

Некоторые проверки ограничиваются учётными записями с `adminCount=1` — AD отмечает так записи, состоящие или ранее состоявшие в привилегированных группах:

| Проверка | Область LDAP | Дополнительная проверка |
|-------|------------|----------------------|
| **Get-InactiveAdminAccounts** | `adminCount=1` и только включённые записи | `Test-AccountActivity` для обнаружения неактивности |
| **Get-AdminPasswordNeverExpires** | `adminCount=1` и бессрочный пароль | `Test-IsPrivileged` для исключения устаревшего adminCount |
| **Get-AdminReversibleEncryption** | `adminCount=1` и обратимое шифрование | Нет (любая такая административная запись — находка) |

**Об оставшемся adminCount:** при исключении пользователя из привилегированной группы AD **не снимает автоматически** `adminCount=1`. Get-AdminPasswordNeverExpires с помощью `Test-IsPrivileged` проверяет, остаётся ли запись действительно привилегированной, а случаи устаревшего adminCount отмечает отдельно.

### <a id="disabled-account-handling"></a>Обработка отключённых учётных записей

adPEAS **не исключает отключённые учётные записи глобально**. Большинство проверок возвращает и включённые, и отключённые записи: отключённая запись остаётся риском для того, кто сможет включить её и воспользоваться ранее назначенными правами.

Исключение — проверки Kerberos. Они пропускают отключённые записи по причине работы протокола, а не предпочтений аудитора: на запрос билета для отключённого субъекта KDC отвечает KDC_ERR_CLIENT_REVOKED, поэтому получить билет для взлома и злоупотребить делегированием невозможно, пока запись отключена.

Проверки, запрашивающие из AD только включённые записи:

| Проверка | Причина |
|-------|-----|
| **Get-KerberoastableAccounts** | KDC не выдаёт сервисный билет для отключённой записи; хеш для подбора недоступен |
| **Get-ASREPRoastableAccounts** | Аналогично: AS-REP для отключённой записи не выдаётся |
| **Get-UnconstrainedDelegation** | Делегирование выполняет запись, способная пройти аутентификацию |
| **Get-ConstrainedDelegation** | То же для обеих рассматриваемых совокупностей |
| **Get-ResourceBasedConstrainedDelegation** | Аналогично |
| **Get-InactiveAdminAccounts** | Только включённые записи — цель: найти *действующих*, но не используемых администраторов |
| **Get-LAPSPermissions** | Только включённые компьютеры — пароли LAPS отключённых компьютеров не используются при текущем доступе |

Даже отключённая запись с SPN или делегированием представляет интерес, если её можно включить: для оценки нужно знать, кто может изменять запись. Это проверяют `Get-PasswordResetRights` и `Get-DangerousACLs`, а не запрос билета, который KDC не выдаёт.

## <a id="overview"></a>Обзор

adPEAS выполняет более 43 проверок безопасности, организованных в десять категорий. Все модули
выполняются по умолчанию, **кроме Shares**: его требуется явно запросить (`-Module Shares`), поскольку он открывает
SMB-соединение со всеми компьютерами Windows домена, что должно быть осознанным решением
оператора аудита.

| Модуль | Проверок | Назначение |
| ------------- | ------ | ----------------------------------------- |
| Domain | 5 | Конфигурация домена, доверия и политики |
| Creds | 7 | Способы раскрытия учётных данных |
| Rights | 6 | Анализ ACL и разрешений |
| Delegation | 3 | Ошибки настройки делегирования Kerberos |
| ADCS | 2 | Уязвимости служб сертификатов |
| Accounts | 9 | Привилегированные записи и параметры безопасности |
| GPO | 4 | Безопасность групповых политик |
| Computer | 6 | Безопасность компьютерных учётных записей |
| Application | 3 | Инфраструктура корпоративных приложений |
| Shares | 1 | Доступные общие ресурсы и учётные данные на них (только по запросу) |

## <a id="domain-module"></a>Модуль Domain

Анализирует конфигурацию домена и параметры его безопасности.

### Get-DomainInformation

**Назначение**: получает общую информацию о домене и его функциональном уровне.

**Что проверяется**:
- Функциональный уровень домена.
- Функциональный уровень леса.
- Контроллеры домена.
- Что остаётся после удаления объекта в лесу: срок хранения объектов-заглушек (`tombstoneLifetime` в `CN=Directory Service`, 60 дней при отсутствии настройки; значение меньше 180 дней нового леса — сигнал: более старая резервная копия уже не может быть восстановлена) и включена ли корзина AD (по `msDS-EnabledFeature` в контейнере Partitions; отключённая корзина при уровне леса 2008 R2 или выше — сигнал), а также срок хранения удалённых объектов при включённой корзине.
- Какая служба реплицирует SYSVOL: DFSR, FRS или обе, пока миграция не достигла состояния Eliminated. Данные читаются из набора реплик FRS и группы репликации DFSR для SYSVOL в `CN=System`, а также из глобального состояния в `msDFSR-Flags`. FRS — сигнал риска: технология устарела, и контроллер Windows Server 1709 или новее в такой домен добавить нельзя.

**Влияние на безопасность**: устаревшие функциональные уровни могут не поддерживать защитные механизмы и указывать на наличие старых уязвимых DC.

| Функциональный уровень | Серьёзность |
|-----------------|----------|
| Windows 2000/2003 | Критическая (EOL) |
| Windows 2008/R2 | Высокая (EOL) |
| Windows 2012/R2 | Средняя |
| Windows 2016 | Низкая |
| Windows 2019+ | Информационная |

**Использование**:
```powershell
Get-DomainInformation
```

---

### Get-DomainPasswordPolicy

**Назначение**: анализирует политику паролей домена по умолчанию.

**Что проверяется**:
- Максимальный срок действия пароля (отключён — пароли бессрочны).
- Минимальная длина пароля (меньше 8 — слабая политика).
- Требование сложности паролей.
- Порог блокировки учётной записи.
- Настройка обратимого шифрования.
- История паролей (`pwdHistoryLength`): значение 0 позволяет сразу вернуть пароль, заменённый при сбросе, — предупреждающий признак; стандартная настройка Microsoft запоминает 24 пароля.
- Детальные политики паролей Fine-Grained Password Policies: те же параметры (длина, сложность, обратимое шифрование, порог и продолжительность блокировки, окно наблюдения, минимальный и максимальный возраст, история паролей), приоритет и объекты применения.
- Без прав Domain Admin параметры политик по умолчанию прочитать нельзя; вместо этого определяются их имена и назначения: перечисляется Password Settings Container (содержит имена всех политик без атрибутов), `msDS-PSOApplied` на соответствующих пользователях и группах и `msDS-ResultantPSO` текущей учётной записи. Возвращаются имена и прямые назначения, но не настройки.

**Влияние на безопасность**: слабая парольная политика упрощает подбор паролей и атаки перебором без блокировки.

**Использование**:
```powershell
Get-DomainPasswordPolicy
```

---

### Get-DomainTrusts

**Назначение**: перечисляет доверительные отношения доменов и лесов.

**Что проверяется**:
- Направление доверия (входящее, исходящее, двустороннее).
- Тип доверия (лес, внешнее, сокращённое).
- Состояние фильтрации SID.
- Настройки выборочной аутентификации.
- Типы шифрования Kerberos, разрешённые между доверенными доменами, по `msDS-SupportedEncryptionTypes` объекта доверия. Если атрибут отсутствует, доверие использует RC4 без AES (KB4492348); изменение 2026 года, сделавшее AES типом по умолчанию для учётных записей, не распространяется на доверия. Отсутствие AES — предупреждающий признак.
- SID домена-партнёра (`securityIdentifier` в объекте доверия).
- Для доверия, при котором партнёр доверяет этому домену, — время последней смены пароля междоменной учётной записи `<flatName>$`. Доверяющий домен меняет его примерно раз в 30 дней; 90 дней и более — сигнал остановки ротации, когда ранее извлечённый ключ доверия остаётся действительным.

**Влияние на безопасность**: внешние доверия могут позволить горизонтальное перемещение по сети. Двусторонние доверия затрагивают оба домена. Отключённая фильтрация SID допускает атаки через SID History. Отсутствие AES оставляет RC4 на границе доверия; если для доверия с MIT Kerberos пароль выбран администратором, ключ доверия может быть подобран автономно по referral-билету.

**Использование**:
```powershell
Get-DomainTrusts
```

---

### Get-LDAPConfiguration

**Назначение**: проверяет настройки безопасности LDAP на контроллерах домена.

**Что проверяется**:
- Обязательность подписи LDAP.
- Принудительная привязка канала LDAP (channel binding).
- `dsHeuristics` в `CN=Directory Service` — одна строка на весь лес, не управляемая
  GPO. Четыре символа могут отключить защиту сразу на всех контроллерах домена:
  - символ 7: анонимные LDAP-операции за пределами rootDSE.
  - символ 8: анонимные вызовы интерфейса адресной книги NSPI.
  - символ 16: исключение групп Account, Server, Print или Backup Operators и
    их участников из защиты AdminSDHolder.
  - символ 21: отключение проверок уникальности UPN, SPN и псевдонимов SPN.

  Символ вне определённых спецификацией значений обозначается как неизвестный, без
  приписывания ему значения.

**Влияние на безопасность**: отсутствие подписи LDAP допускает атаки «человек посередине». Анонимный доступ позволяет разведку без учётных данных. Группа операторов, исключённая из AdminSDHolder, сохраняет назначенные ей и участникам права, а такие группы могут влиять на контроллеры домена. При отключённой проверке псевдонимов SPN субъект с правом записи SPN может присвоить своей записи имя службы сервера.

**Использование**:
```powershell
Get-LDAPConfiguration
```

---

### Get-SMBSigningStatus

**Назначение**: проверяет подпись SMB на контроллерах домена.

**Что проверяется**:
- Требование подписи SMB на контроллерах домена.
- Состояние включения подписи SMB.

**Влияние на безопасность**: без подписи SMB возможны атаки ретрансляции SMB, перехват и перенаправление аутентификации.

**Использование**:
```powershell
Get-SMBSigningStatus
```

## <a id="creds-module"></a>Модуль Creds

Выявляет способы раскрытия учётных данных.

### Get-LAPSCredentialAccess

**Назначение**: проверяет, может ли текущий пользователь читать пароли LAPS.

**Что проверяется**:
- Фактический доступ на чтение атрибутов пароля LAPS.
- У каких компьютеров текущему пользователю доступны пароли LAPS.

**Влияние на безопасность**: чтение паролей LAPS даёт доступ к учётным данным локальных администраторов соответствующих компьютеров и может позволить горизонтальное перемещение.

**Использование**:
```powershell
Get-LAPSCredentialAccess
```

---

### Get-BitLockerRecoveryKeyAccess

**Назначение**: проверяет, какие ключи восстановления BitLocker текущий пользователь может читать из AD.

**Что проверяется**:
- Доступные для чтения `msFVE-RecoveryPassword` у объектов `msFVE-RecoveryInformation` (дочерних объектов компьютера).
- 48-значный пароль восстановления, GUID восстановления/тома и время сохранения в AD.
- Компьютер, к которому относится ключ (определяется по родительскому DN).

**Как работает**: один запрос по поддереву с серверным фильтром `(&(objectClass=msFVE-RecoveryInformation)(msFVE-RecoveryPassword=*))` для всего домена. Фильтр наличия атрибута учитывает ACL, поэтому DC возвращает только объекты восстановления, пароль которых текущему пользователю действительно разрешено читать; отдельного перебора каждого компьютера нет. Если хранение ключей BitLocker в домене не применяется (нет схемы/объектов `msFVE-RecoveryInformation`), дорогостоящий запрос пропускается, а результат кешируется до конца сеанса.

**Влияние на безопасность**: чтение ключа нередко законно для служб поддержки и восстановления, поэтому отмечается как *подсказка*, а не находка. Прочитанный ключ позволяет разблокировать защищённый BitLocker том в автономном режиме при физическом доступе или наличии образа диска; чрезмерно широкое чтение может указывать на избыточное делегирование в OU компьютеров.

**Кто ещё может читать**: дополнительный раздел перечисляет субъектов с делегированным правом чтения `msFVE-RecoveryPassword` на контейнерах компьютеров (включая отключённые компьютеры: их пароль восстановления остаётся действительным для диска) через `Get-OUPermissions -CheckType BitLocker`. В схеме атрибут конфиденциальный, а чтение объектов `msFVE-RecoveryInformation` по умолчанию доступно лишь Domain Admins и SYSTEM; нужны **одновременно** `ReadProperty` и `ControlAccess` на этих объектах. Обе части права объединяются по контейнеру, а строка показывает, действует ли оно сейчас, блокируется конфиденциальным флагом (*подсказка*, станет действующим при снятии флага) или невозможно определить из-за недоступности схемы. Один `ControlAccess` без чтения ничего не даёт и не отображается. ACE, заданные непосредственно на одном компьютере или объекте восстановления, не выявляются. Привилегированные субъекты скрыты без `-IncludePrivileged`.

**Использование**:
```powershell
Get-BitLockerRecoveryKeyAccess

# Также показать привилегированных субъектов с делегированным чтением
Get-BitLockerRecoveryKeyAccess -IncludePrivileged
```

### Get-CredentialRoaming

**Назначение**: сообщает о пользователях, чьи мастер-ключи DPAPI и закрытые ключи сохраняются в AD, и о возможности чтения этого материала другими субъектами.

**Что проверяется**:
- Какие пользователи имеют синхронизированный материал учётных данных (`msPKIDPAPIMasterKeys`, `msPKIAccountCredentials`) и когда он синхронизирован (`msPKIRoamingTimeStamp`).
- Отмечены ли оба атрибута как конфиденциальные в схеме (`searchFlags`, бит 7, `fCONFIDENTIAL` = 128).
- Какие субъекты обладают **делегированным** чтением атрибутов на содержащих материал контейнерах.
- Есть ли привилегированные записи среди затронутых пользователей и субъектов с делегированными правами.

**Как работает**: используются два серверных фильтра наличия — `(msPKIDPAPIMasterKeys=*)` и `(msPKIAccountCredentials=*)`. Содержимое BLOB-атрибутов намеренно **не извлекается**: передаются только имя записи, DN и время. Для аудита шифротекст не нужен, а помещение DPAPI-ключей в Base64 в HTML-отчёт само создало бы выявляемую утечку. Оба атрибута исключены из отображения централизованно, поэтому их не выводят другие проверки. Флаг конфиденциальности однократно для леса определяется по двум объектам `attributeSchema`; имена объектов схемы (`ms-PKI-DPAPIMasterKeys`) отличаются от имён атрибутов, поэтому проверяются оба варианта. Результат определяется по менее защищённому атрибуту; если схема недоступна, состояние обозначается *неизвестным*, а не подтверждённо безопасным или опасным. Затем `Get-OUPermissions -CheckType CredentialRoaming` проверяет делегированные ACE чтения контейнеров, содержащих пользователей, один раз на контейнер, а не на пользователя: DACL контейнера уже содержит унаследованные права.

**Влияние на безопасность**: атрибуты содержат шифротекст, не открытый текст. Мастер-ключ запечатан предварительным ключом из пароля пользователя **и** резервным ключом домена, закрытые ключи запечатаны мастер-ключами. Само наличие такого материала — *подсказка*: закрытые ключи хранятся в AD, хотя не обязаны, и могут быть использованы после получения хеша пользователя либо резервного ключа домена. Если материал может читать низкопривилегированный субъект, это *находка*: без флага конфиденциальности чтение следует обычным ACE объекта пользователя, и в типовом домене любой аутентифицированный пользователь может собрать синхронизированный материал других пользователей обычным LDAP-чтением. Вместе с резервным ключом домена (доступным каждому администратору домена) это позволяет восстановить чужие закрытые ключи автономно, а сертификат клиентской аутентификации затем позволяет войти как этот пользователь без пароля. Эти ограничения не распространяются на субъекты с DCSync, копией `ntds.dit` либо резервной копией AD.

**Делегированное чтение**: конфиденциальный флаг регулирует общий доступ, но сам по себе ничего не говорит о делегированных правах, которые могут быть выданы ошибочно. Применимость ACE зависит от схемы: одна и та же ACE в одном лесу является *находкой*, в другом — пока не действующей *подсказкой*:

| ACE предоставляет | Атрибуты конфиденциальны | Оценка |
|---|---|---|
| `ReadProperty` | нет | действует сейчас — находка |
| `ReadProperty` | да | блокируется флагом — подсказка (начнёт действовать после его снятия) |
| `ReadProperty` + `ControlAccess` либо `GenericAll` | любое значение | действует сейчас — находка |

ACE с одним `ControlAccess`, ограниченным определённым атрибутом, учитывается как право: в типовом ACL `ReadProperty` обычно уже доступно всем аутентифицированным пользователям без отдельного делегирования. *Неограниченная* ACE `ControlAccess` («все расширенные права») здесь не заявляется — её анализирует `Get-DangerousACLs`. Чтение лишь `ms-PKI-RoamingTimeStamp` оценивается как Low и скрывается из отчёта по умолчанию: время — не учётные данные. Привилегированные субъекты скрыты без `-IncludePrivileged`.

**Не охватывается**: ACE, назначенная непосредственно объекту одного пользователя в обход контейнера, и делегирование на контейнере, пользователи которого никогда ничего не синхронизировали. Там пока нечего читать, но это станет видно при первой синхронизации.

**Использование**:
```powershell
Get-CredentialRoaming

# Также показать привилегированных субъектов с делегированным чтением
Get-CredentialRoaming -IncludePrivileged
```

### Get-CredentialExposure

**Назначение**: выявляет учётные данные в SYSVOL, сценариях NETLOGON и Group Policy Preferences.

**Что проверяется**:
- Пароли GPP в XML-файлах SYSVOL (атрибут cpassword, MS14-025).
- Пароли AutoAdminLogon в Registry.xml (открытый текст).
- Учётные данные, записанные непосредственно в сценариях NETLOGON/SYSVOL и файлах настроек (.bat, .cmd, .ps1, .psm1, .psd1, .vbs, .vbe, .kix, .txt, .ini, .inf, .conf, .cnf, .config, .json, .yml, .yaml, .reg, .vnc) и файлах комментариев GPO (.cmtx). Исключён GptTmpl.inf: в нём каждое совпадение относится к парольной политике; Registry.pol разбирается отдельно для поиска значений паролей.
- Расшифровываемые пароли VNC: файлы подключения VNC Viewer (.vnc, с указанным в них узлом), .ini UltraVNC и TightVNC, а также параметры реестра, раздаваемые политикой для RealVNC, TightVNC, TigerVNC и UltraVNC (REG_SZ/REG_BINARY). Все эти реализации VNC шифруют пароль одним опубликованным ключом DES, поэтому сохранённое значение фактически является паролем.
- Пароли из файлов ответов Windows (unattend XML, распознаваемых по корневому элементу): пароли администратора, локальных записей, автоматического входа, присоединения к домену; скрытые Windows SIM значения декодируются.
- Команды net use, содержащие пароли.
- Закодированные сценарии VBScript (.vbe, декодируются автоматически).
- Произвольные UNC-пути и локальные каталоги (автономный режим).

**Уровни достоверности обнаружения**:

| Уровень | Серьёзность | Примеры шаблонов |
|------|----------|-----------------|
| Уровень 1 (высокая достоверность) | Находка | GPP cpassword, `password=Secret123`, `net use ... /user:admin pass`, PSExec с `-p`, строки подключения |
| Уровень 2 (ниже достоверность) | Подсказка | Общие упоминания `password`, `credential`, парольные элементы XML |

**Влияние на безопасность**: GPP использует опубликованный ключ Microsoft AES, VNC — опубликованный DES; оба легко расшифровать. Учётные данные из сценариев SYSVOL доступны всем аутентифицированным пользователям домена.

**Запись, которой принадлежат учётные данные**: пароли GPP, значения AutoAdminLogon и команды `net use` сопровождаются строкой `accountInAD`. Она показывает, существует ли одноимённая доменная запись, включена ли она, привилегирована ли, а также менялся ли пароль после последней записи файла. Переменные, локальные и встроенные учётные записи, имена из другого домена или компьютера и записи из `Groups.xml` (по определению локальные) обозначаются отдельно, а не ищутся в AD. При отсутствии сеанса каталога строка не выводится.

**Использование**:
```powershell
# Сканирование доменных SYSVOL/NETLOGON
Get-CredentialExposure

# Произвольный UNC-путь (нужен отдельный сеанс Connect-adPEAS либо -Credential)
Get-CredentialExposure -Path "\\server\share"
```

### Get-DeletedObjectAccess

**Назначение**: проверяет, какие удалённые объекты читает текущий пользователь, остались ли в них учётные данные и кто ещё вправе их перечислять.

**Что проверяется**:
- Все удалённые объекты, перечисляемые текущим пользователем в контейнере Deleted Objects домена; контейнер определяется по well-known GUID, чтение выполняется с контролем показа удалённых (`1.2.840.113556.1.4.417`).
- Читает ли пользователь через членство в Administrators или благодаря делегированию на контейнере; второй вариант — *подсказка*.
- Текстовые атрибуты, проверяемые `Get-PasswordInDescription`, с теми же шаблонами из `Get-CredentialTextMatch`, и Unix-атрибуты пароля из `Get-UnixPasswordAccounts`.
- Субъекты вне Tier 0, которым разрешено перечислять контейнер: применимая к нему ACE с List Contents, общим чтением, полным контролем, а также владелец контейнера.

**Влияние на безопасность**: при включённой корзине AD удалённый объект сохраняет все атрибуты в Deleted Objects до истечения срока хранения удалённых объектов — по умолчанию 180 дней. Пароль, вписанный в описание служебной записи, остаётся после её удаления; проверки действующих объектов больше его не видят. По умолчанию контейнер перечисляют лишь SYSTEM и Administrators (наблюдение: обычный пользователь видит только DN). Microsoft описывает выдачу List Contents и Read Property для доступа службы поддержки к удалённым объектам. Удалённый объект сохраняет собственный дескриптор безопасности, поэтому обладатель права перечислять контейнер читает в каждом объекте лишь разрешённые его ACL поля. Широкая группа с таким правом — *находка*, прочий субъект — *подсказка*.

**Не охватывается**: ACL контейнера по умолчанию читают только администраторы; у обычного пользователя проверка сообщает об этом. Для восстановления удалённых объектов необходимо право Reanimate-Tombstones на корне раздела именования, о котором сообщают `Get-DangerousACLs` для домена и `Get-CriticalObjectACLs` для раздела конфигурации. Включение корзины и сроки хранения показываются `Get-DomainInformation`.

**Использование**:
```powershell
Get-DeletedObjectAccess

# Также перечислить Tier 0 и служебные группы Exchange
Get-DeletedObjectAccess -IncludePrivileged
```

### Get-CriticalObjectACLs

**Назначение**: ищет субъектов вне Tier 0, которые контролируют схему, раздел конфигурации, контейнер Partitions, RID Manager, объект Infrastructure или сайт.

**Что проверяется**:
- Корень раздела схемы, корень раздела конфигурации, `CN=Partitions` в конфигурации, `CN=RID Manager$,CN=System` и `CN=Infrastructure`.
- Владелец и права GenericAll, GenericWrite, WriteDacl, WriteOwner, а также неограниченное WriteProperty на каждом объекте.
- Право передачи роли на каждом объекте (Change-Schema-Master, Change-Domain-Master, Change-Rid-Master, Change-Infrastructure-Master) и все расширенные права.
- Reanimate-Tombstones на корне конфигурации — это право проверяется при восстановлении удалённых объектов конфигурации, включая шаблоны сертификатов. По умолчанию здесь его имеют только Enterprise Admins. На корне схемы оно не проверяется: объекты схемы нельзя удалить.
- WriteProperty на `rIDAvailablePool` у RID Manager.
- WriteProperty на `gPLink` каждого сайта: привязанная туда GPO достигает всех компьютеров сайта, включая контроллеры домена.
- Группы операторов считаются находящимися вне Tier 0.

**Влияние на безопасность**: контроль над схемой меняет дескриптор безопасности по умолчанию всех новых объектов леса; контроль над объектом роли позволяет передать роль мастера операций, а пул RID можно исчерпать.

```powershell
Get-CriticalObjectACLs
```

### Get-GPOUserRightsAssignment

**Назначение**: сравнивает пользовательские права Windows, выдаваемые GPO, со штатным набором Windows и сообщает об отклонениях.

**Почему сравнение**: раздел `[Privilege Rights]` файла `GptTmpl.inf` задаёт права абсолютно, а не дополняет существующие. Субъекты, перечисленные GPO для определённого права, становятся полным набором обладателей этого права на каждом компьютере, где применяется политика. Список GPO и документированный стандартный список описывают одно и то же; важны различия в обе стороны.

**Что проверяется**:
- Раздел `[Privilege Rights]` файла `GptTmpl.inf` каждой GPO.
- **Обладатели сверх штатных Windows** — риск повышения привилегий; серьёзность зависит от самого права. Права повышения привилегий и доступа к учётным данным (SeDebug, SeBackup, SeRestore, SeTakeOwnership, SeImpersonate, SeAssignPrimaryToken, SeCreateToken, SeTcb, SeLoadDriver, SeEnableDelegation, SeSyncAgent, SeManageVolume, SeSecurity, SeRelabel, SeTrustedCredManAccess) относятся к находкам; права входа (RDP, вход службой, пакетное задание, интерактивный вход, изменение времени, выключение) — к подсказкам.
- **Штатные обладатели, удалённые политикой** — примечание. Чаще осознанное ужесточение, иногда причина отказа службы.
- Права, выданные широким группам (Everyone, Authenticated Users, Domain Users), всегда повышаются до находки.
- Верный эталон для затронутых компьютеров: у контроллеров домена и рядовых узлов наборы различаются; политика для обоих сравнивается с их объединением.
- Применяется ли GPO сейчас вообще (отключённая часть, нет привязки).
- Привязки каждой находки к затронутым OU и ко всему домену по связям GPO.

**Почему не фильтровать по субъекту**: скрытие привилегированных SID, групп операторов и служебных идентификаторов даёт ошибки в обе стороны. Например, `Backup Operators` с `SeDebugPrivilege` — не штатное право Windows, а прямой путь к SYSTEM; фильтр по субъекту скрыл бы его как «привилегированную группу». При этом штатные обладатели права зависят от конкретного права, а не только от уровня привилегий субъекта.

**Пробелы эталона показываются, а не домысливаются**: если для права штатный набор неизвестен, эталон не назначается, и это явно отмечается. Пример — `SeServiceLogonRight`, зависящее от установленных продуктов; только для этого права проверка использует резервную фильтрацию по идентификаторам.

**Влияние на безопасность**: одна GPO может выдать низкоуровневые права (например, SeDebugPrivilege → SYSTEM, SeBackupPrivilege → чтение SAM/NTDS) всем компьютерам своей области. Это может стать прямым, иногда доменным путём повышения привилегий и перемещения между узлами. `SeMachineAccountPrivilege` анализируется отдельно в Get-AddComputerRights, а запрещающие права `Se*Deny*`, отнимающие доступ, не оцениваются.

**Использование**:
```powershell
# Показать назначения, отклоняющиеся от штатного набора Windows (по умолчанию)
Get-GPOUserRightsAssignment

# Показать все назначения, включая соответствующие штатному набору
Get-GPOUserRightsAssignment -IncludeDefaults
```

**Параметры**:

| Параметр | Описание |
|-----------|-------------|
| `-IncludeDefaults` | Дополнительно показывать назначения, совпадающие со штатными Windows |
| `-IncludePrivileged` | Псевдоним `-IncludeDefaults` для совместимости со старыми вызовами |

### Get-ADCSVulnerabilities

**Назначение**: выявляет уязвимые настройки AD CS.

**Что проверяется**:

| ESC | Уязвимость |
| ----- | -------------------------------------------------------- |
| ESC1 | Шаблон допускает SAN от заявителя и клиентскую аутентификацию |
| ESC2 | Шаблон допускает EKU Any Purpose |
| ESC3 | Злоупотребление шаблоном агента регистрации (шаблон агента и целевой шаблон) |
| ESC4 | Уязвимые ACL шаблона |
| ESC5 | Уязвимые разрешения контейнеров PKI |
| ESC8 | Проверка веб-регистрации (HTTP/HTTPS и настройки NTLM/EPA) |
| ESC9 | Нет расширения безопасности + клиентская аутентификация |
| ESC13 | Политика выдачи, связанная с группой AD |
| ESC15 | Схема v1 и Subject от заявителя (CVE-2024-49019) |

Ещё две проблемы обнаруживаются другими проверками, потому что ошибки настройки находятся не в
шаблоне или УЦ:

| ESC | Уязвимость | Проверка |
| ----- | -------------------------------------------------------- | ----- |
| ESC10 | Слабое сопоставление сертификатов на DC — `StrongCertificateBindingEnforcement=0` либо бит UPN в `CertificateMappingMethods` | `Get-GPORegistrySettings`, если значения назначены групповой политикой |
| ESC14 | Слабое явное сопоставление `altSecurityIdentities` и право записи этого атрибута у привилегированной записи | `Get-WeakCertificateMapping` |

**Преднамеренно не реализовано**: ESC6 (`EDITF_ATTRIBUTESUBJECTALTNAME2`), ESC7
(`ManageCA` / `ManageCertificates`), ESC11 (`IF_ENFORCEENCRYPTICERTREQUEST`) и ESC16
(`DisableExtensionList`).

Все четыре параметра находятся в реестре сервера УЦ по пути
`HKLM\SYSTEM\CurrentControlSet\Services\CertSvc\Configuration`; для чтения нужны
права администратора на этом сервере: удалённый реестр от локального администратора либо
RPC-интерфейс `ICertAdminD2` с разрешением `ManageCA`. adPEAS рассчитан на запуск обычным
пользователем домена. Проверка, которая обычно отвечает «невозможно определить», хуже её отсутствия:
пустой вывод воспринимается как безопасный домен. При наличии нужных прав все
четыре параметра проверяет Certipy.

ESC12 (закрытый ключ на YubiHSM, извлекаемый при доступе к оболочке УЦ) не виден
при сканировании каталога.

**Подробности ESC5**: проверяются опасные разрешения на объектах контейнеров PKI:
- `CN=Public Key Services` — корневой контейнер PKI.
- `CN=Certificate Templates` — позволяет создавать или менять шаблоны.
- `CN=Enrollment Services` — управляет службами выдачи.
- `CN=NTAuthCertificates` — определяет доверенные УЦ для Kerberos.
- `CN=AIA` — сертификаты УЦ, опубликованные для построения цепочек.
- `CN=CDP` — расположения списков отзыва.
- `CN=OID` — политики выдачи (связаны с ESC13).

Опасные права: GenericAll, WriteDacl, WriteOwner, GenericWrite. При наличии у непривилегированных пользователей они позволяют изменять инфраструктуру PKI.

**Хранилище NTAuth**: каждый сертификат в `CN=NTAuthCertificates` задаёт издателя, которому доверена выдача сертификатов для входа от имени любой записи. Enterprise CA публикует там свой сертификат, поэтому для каждой записи выводится `EnterpriseCA`: УЦ этого леса, которому она принадлежит; старый сертификат перевыпущенного УЦ либо отсутствие соответствия — сторонний, автономный или удалённый УЦ (требует проверки как *подсказка*). Истёкшие и подписанные SHA1/MD5 записи также отмечаются подсказками; раздел сообщает, когда доверено несколько УЦ. Издатель, добавленный только на отдельном компьютере через `certutil -enterprise -addstore NTAuth`, в каталоге не хранится и не обнаруживается.

**Влияние на безопасность**: уязвимости AD CS могут позволить любому пользователю домена получить сертификат на имя другого, включая Domain Admins, вплоть до полного захвата домена.

**Использование**:
```powershell
# По умолчанию: непривилегированные записи с правами регистрации сертификатов
Get-ADCSVulnerabilities

# Также включить привилегированные записи (Domain Admins, Enterprise Admins и др.)
Get-ADCSVulnerabilities -IncludePrivileged
```

**Параметры**:

| Параметр | Описание |
|-----------|-------------|
| `-IncludePrivileged` | Включить в вывод привилегированные записи (жёлтая подсветка) |

## <a id="accounts-module"></a>Модуль Accounts

Анализирует безопасность привилегированных учётных записей.

### Get-PrivilegedGroupMembers

**Назначение**: перечисляет участников привилегированных групп.

**Что проверяется**:
- Участники Domain Admins.
- Участники Enterprise Admins.
- Участники Schema Admins.
- Участники Administrators.
- Участники Account Operators.
- Участники Backup Operators.
- Участники Server Operators.
- Участники Print Operators.

**Влияние на безопасность**: выявляет все учётные записи с повышенными привилегиями. Чем их больше, тем шире поверхность атак.

**Привилегированные группы без защиты AdminSDHolder**: SDProp восстанавливает DACL защищённых групп по шаблону AdminSDHolder (список Microsoft: Account Operators, Administrators, Backup Operators, Domain Admins, Domain Controllers, Enterprise Admins, Enterprise Key Admins, Key Admins, Print Operators, Read-only Domain Controllers, Replicator, Schema Admins, Server Operators), который читает проверка. Все остальные привилегированные группы сохраняют собственные ACE. Поэтому проверка также читает DACL и владельца каждой привилегированной группы без `adminCount=1`, каждой вложенной в неё группы и групп Exchange в `OU=Microsoft Exchange Security Groups`. С учётом явных и наследуемых ACE и той же классификации субъектов, что для AdminSDHolder, выводятся те, кто может изменять атрибут `member` (или все атрибуты), воспользоваться валидируемой записью Self-Membership, менять DACL/владельца, имеет полный контроль или владеет группой. Это *находка*, если захват группы критичен для домена (DnsAdmins, ESX Admins, группы Exchange, группы, достижимые из Tier 0), и *подсказка*, если все затронутые группы лишь операторского уровня (Group Policy Creator Owners, Cert Publishers, Remote Management Users, Hyper-V Administrators, группа, вложенная в Backup Operators). Перечень прочитанных и недоступных групп выводится одним объектом в начале раздела. Account Operators по стандартному дескриптору класса групп контролируют все незащищённые группы; это отмечается одной *подсказкой*, пока в Account Operators есть участники, а не повторяется для каждой группы. Группа, ранее защищённая и сохранившая устаревший `adminCount=1`, обычно не читается. Исключение: символ 16 `dsHeuristics` выводит группы Account, Server, Print или Backup Operators из-под защиты AdminSDHolder; тогда они и группы, достижимые только через них, читаются независимо от `adminCount` и перечисляются в сводке. Группы другого домена не анализируются.

**Кто может захватить привилегированную учётную запись**: проверка читает DACL и владельца всех найденных привилегированных пользователей и управляемых служебных записей этого домена. Компьютеры обрабатывает `Get-NonDefaultComputerOwners`, читающий явные ACE на каждом компьютере. Показываются права полного контроля, изменения DACL или владельца, записи всех атрибутов, всех расширенных прав, сброса пароля, изменения `msDS-KeyCredentialLink` (теневые учётные данные), `servicePrincipalName` (целевой Kerberoasting), `altSecurityIdentities` (сопоставление сертификата), `userAccountControl` или User-Account-Restrictions, `scriptPath`, а для gMSA — `msDS-GroupMSAMembership`, а также фактический владелец. Учитываются явные и унаследованные ACE с прежней фильтрацией по субъекту. Это *находка*, когда запись принадлежит группе, критичной для домена (Tier 0 либо вложенная в неё, DnsAdmins, ESX Admins), и *подсказка*, когда все членства только операторского уровня (Group Policy Creator Owners, Cert Publishers, Backup Operators и т. д.). Число прочитанных, защищённых AdminSDHolder и недоступных записей выводится одним объектом в начале раздела. Для записи с `adminCount=1` право, выданное шаблоном AdminSDHolder тому же субъекту, показывается один раз в строке AdminSDHolder; индивидуальные дополнения также выводятся. Key Admins и Enterprise Key Admins штатно могут писать `msDS-KeyCredentialLink`; Account Operators штатным дескриптором класса пользователя контролируют все записи, которые не защищены AdminSDHolder — это отмечается одной строкой.

**Использование**:
```powershell
# По умолчанию: непривилегированные субъекты с членством в группах
Get-PrivilegedGroupMembers

# Включить в вывод привилегированные записи (Domain Admins и др.)
Get-PrivilegedGroupMembers -IncludePrivileged
```

**Параметры**:

| Параметр | Описание |
|-----------|-------------|
| `-IncludePrivileged` | Включить в вывод привилегированные записи (жёлтая подсветка) |

### Get-SIDHistoryInjection

**Назначение**: ищет учётные записи с привилегированными SID в sIDHistory (возможное внедрение SID History).

**Что проверяется**:
- Пользователи и компьютеры с заполненным sIDHistory.
- Привилегированные SID в sIDHistory (Domain Admins, Enterprise Admins, Administrators и др.).
- SID групп операторов (Account Operators, Backup Operators и др.).
- Непривилегированные SID как следы миграции (необязательно).

**Влияние на безопасность**: внедрение SID History позволяет добавить привилегированные SID в sIDHistory записи и получить соответствующие права без прямого членства в привилегированной группе. Это критический способ закрепления доступа и повышения привилегий.

| Тип SID в sIDHistory | Серьёзность |
|-----------------------|----------|
| Domain Admins (-512) | Критическая |
| Enterprise Admins (-519) | Критическая |
| Administrators (S-1-5-32-544) | Критическая |
| Account Operators (S-1-5-32-548) | Высокая |
| Backup Operators (S-1-5-32-551) | Высокая |
| Непривилегированные SID | Информационная (след миграции) |

**Использование**:
```powershell
# Проверять только привилегированные SID
Get-SIDHistoryInjection

# Также включать непривилегированные SID (следы миграции)
Get-SIDHistoryInjection -IncludeNonPrivileged
```

**Параметры**:

| Параметр | Описание |
|-----------|-------------|
| `-IncludeNonPrivileged` | Также выводить записи, чей sIDHistory содержит только непривилегированные SID (следы миграции); они появляются отдельным разделом как подсказки. Без ключа показываются только записи с привилегированными SID (Domain Admins, группы операторов и др.). |

**Возвращаемые свойства**:
- `privilegedSIDHistory`: форматированный список найденных привилегированных SID.
- `privilegedSIDHistoryCount`: число привилегированных SID.
- `sidHistoryInjectionRisk`: уровень риска (CRITICAL при привилегированных SID).

### Get-ManagedServiceAccountSecurity

**Назначение**: анализирует защищённость управляемых служебных учётных записей (MSA/gMSA).

**Что проверяется**:
- Кто может читать управляемый пароль gMSA.
- Настройки ограниченного делегирования.
- Возраст пароля и состояние ротации.
- Связи делегированных управляемых служебных записей (dMSA, Windows Server 2025) по заменяемым ими учётным записям: связи вне штатной миграции, отсутствующие обратные ссылки, замена привилегированных записей и начатые/завершённые миграции.
- Кто может использовать каждую dMSA (msDS-GroupMSAMembership) и кому принадлежит её дескриптор; оценка аналогична читателям паролей gMSA. Доступно лишь если сканирующий субъект читает dMSA, что по умолчанию требует администратора.

**Влияние на безопасность**: чрезмерно широкое чтение пароля gMSA позволяет получить учётные данные службы. Ошибки делегирования ведут к повышению привилегий. dMSA, связанная с записью, получает от KDC её членства и ключи; связь вне миграции фактически передаёт эту запись субъекту, контролирующему dMSA.

**Использование**:
```powershell
Get-ManagedServiceAccountSecurity
```

### Get-ProtectedUsersStatus

**Назначение**: ищет привилегированные записи, не входящие в группу Protected Users.

**Что проверяется**:
- Членство привилегированных записей в Protected Users.
- Какие административные записи лишены защиты.
- Для записей Tier 0 с назначенной политикой аутентификации или silo: действует ли она реально (enforced, audit only, отсутствует политика, неполное зачисление, переопределение silo либо исключение для встроенного Administrator).

**Влияние на безопасность**: Protected Users запрещает NTLM и делегирование, DES/RC4, ограничивает TGT Kerberos четырьмя часами. Записи вне этой группы сильнее подвержены краже учётных данных.

**Использование**:
```powershell
Get-ProtectedUsersStatus
```

### Get-AuthenticationPolicySilos

**Назначение**: проверяет, ограничивают ли реально кого-либо политики аутентификации и их silo, и кто может менять их.

**Что проверяется**:
- Принудительность каждой silo и политик, назначенных непосредственно записям: в режиме аудита KDC только регистрирует события и никому не отказывает; для участника silo действует флаг самой silo.
- Silo без политики либо без зачисленной записи.
- Неполное зачисление: запись указана участником, но silo ей не назначено, или назначено, но запись отсутствует в списке участников — KDC применяет silo, только когда выполняются оба условия (MS-KILE 3.3.5.4).
- Встроенный Administrator в silo или политике — Windows всегда освобождает его от этих ограничений.
- Условия входа и службы (`AllowedToAuthenticateFrom/To`, выводятся как SDDL), допускающие широкую группу вроде Domain Computers.
- Права записи на silo и политики у субъектов вне Tier 0.
- Время жизни TGT в минутах.
- Если есть условие — поддерживают ли DC claims и Kerberos armoring («KDC support for claims, compound authentication and Kerberos armoring»): читается Registry.pol применяемых к ним GPO с разрешением приоритетов по каждому значению. Без поддержки KDC не способен оценить условия; настройки клиентской части не читаются.

**Влияние на безопасность**: silo не позволяют учётным записям Tier 0 входить на обычные машины. Silo, которая никого не ограничивает, создаёт лишь видимость защиты; тот, кто может менять silo или политику, определяет и ограничения, вплоть до их отсутствия. Silo и политики находятся в разделе конфигурации и читаются любым пользователем домена.

**Использование**:
```powershell
Get-AuthenticationPolicySilos
```

### Get-NonDefaultUserOwners

**Назначение**: ищет пользователей, чей владелец объекта отличается от стандартного.

**Что проверяется**:
- Владелец объекта пользователя (nTSecurityDescriptor).
- Пользователи, чьи владельцы — не Domain Admins.

|------------|----------|
| Domain Admins | Ожидаемо (по умолчанию) |
| Enterprise Admins | Ожидаемо |
| Обычный пользователь | Средняя (риск повышения привилегий) |
| Служебная запись | Средняя |

**Снижение шума**: Exchange Health Mailboxes (`HealthMailbox*` в `CN=Monitoring Mailboxes,CN=Microsoft Exchange System Objects`) по умолчанию исключаются: ожидается, что владельцем является сервер Exchange, создавший такую запись.

**Использование**:

```powershell
# Включая Exchange Health Mailboxes

```

**Параметры**:

| Параметр | Описание |
|-----------|-------------|
| `-IncludeHealthMailboxes` | Включить Exchange Health Mailboxes в результат |

**Возвращаемые свойства**:
- `Owner`: имя владельца объекта пользователя.
- `OwnerSID`: SID владельца.

**Типовые причины**:
- Пользователь создан неадминистратором через делегирование.
- Владелец явно изменён после создания.
- Следы миграции.

### Get-LogonScriptPermissions

**Назначение**: ищет сценарии входа, выполняемые учётными записями, которые могут изменять субъекты помимо администраторов.

**Что проверяется**:
- `scriptPath` каждой включённой записи; относительный путь разрешается в `\\<domain>\NETLOGON\<path>`.
- NTFS-разрешения каждого уникального сценария и его каталога, читаемые через SMB по имени домена и включённым компьютерам домена; используется тот же считыватель, что для сценариев GPO.
- Субъекты записи помимо администраторов и привилегированных записей, число запускающих сценарий записей и имена привилегированных среди них.

**Влияние на безопасность**: Windows запускает сценарий при каждом входе соответствующей учётной записи с её правами. Кто может менять сценарий, может выполнять код от имени каждой записи с этим путём, в том числе от имени администратора. NETLOGON — каталог сценариев в SYSVOL; разрешения его файлов не равны разрешениям GPO.

Локальный путь существует на каждом компьютере и не читается проверкой; для недоступного пути приводится причина. Разрешения общего ресурса отдельно не читаются.

**Использование**:
```powershell
Get-LogonScriptPermissions

# Не устанавливать SMB-соединений: файлы сценариев не читаются
Get-LogonScriptPermissions -OPSEC
```

**Возвращаемые свойства**:
- `logonScript`: UNC-путь к сценарию.
- `logonScriptRisk`: кто может менять сценарий и какие записи затрагиваются.
- `logonScriptPermissions`: одна строка `path: Identity (Rights)` на каждого субъекта помимо администраторов с правом записи сценария или каталога.
- `runByAccounts`: сколько включённых записей запускают сценарий.
- `runByPrivilegedAccounts`: какие из них привилегированные, включая операторов.

## <a id="gpo-module"></a>Модуль GPO

Анализирует безопасность групповых политик.

**Поиск упомянутой GPO в SYSVOL**: каждая находка, связанная с групповой политикой, именует
её одинаково независимо от проверявшего модуля, чтобы объект можно было найти без догадок:

- `GPOName` — отображаемое имя. Удобно, но не уникально и не является путём.
- `GPOGUID` — идентификатор политики, совпадающий с именем её каталога в
  `\\<domain>\SYSVOL\<domain>\Policies\`.
- `GPOPath` — полный путь каталога, записанный в AD в
  `gPCFileSysPath`. Он считывается через LDAP, а не составляется из GUID, поэтому
  одна и та же строка показывается во всех разделах: `gPCFileSysPath` указывает домен, тогда как adPEAS
  читает SYSVOL через определённый контроллер домена; это два разных способа записи пути к
  одной папке.

Проверки, сообщающие о **параметре внутри** политики, дополнительно выводят:

- `SourceFile` — файл относительно каталога GPO, из которого получен параметр,
  например `Machine\Registry.pol` или
  `MACHINE\Microsoft\Windows NT\SecEdit\GptTmpl.inf`. Начальная часть `Machine` или `User`
  имеет значение: в обеих половинах политики бывают одинаково названные файлы, но они действуют
  на разные объекты.

Итак, полный путь к подтверждению находки — `<GPOPath>\<SourceFile>`.

Проверки **самого объекта GPO** — `Get-GPOPermissions`, проверка подписи SMB и LDAP,
`Get-AddComputerRights` — не имеют `SourceFile`: находка относится к политике,
а не к файлу внутри неё. Дополнительно выводится `distinguishedName`,
который отсутствует в находках отдельных параметров. Внутри используются исходные LDAP-
объекты, а три общие строки переименованы лишь для отображения. Поэтому `displayName`, `Name`
и `gPCFileSysPath` сохраняют имена LDAP-свойств и в экспорте JSON.

Осознанное исключение: проверки учётных данных (`Get-CredentialExposure`) выводят
полный путь к файлу в поле `FilePath`, так как также сканируют NETLOGON и указанный
пользователем `-Path`, где нет каталога GPO для относительного пути. Для находки из GPO
полный путь уже содержит GUID.

**Неактивные политики по умолчанию скрываются**: поставщик может развернуть целую библиотеку GPO,
привязать несколько политик, а остальные оставить настроенными, но нигде не применяемыми.
Их параметры заглушили бы сведения о действующих GPO; поэтому находка по непривязанной
или отключённой политике не выводится. Сводная строка показывает число скрытых находок и
число отдельных GPO; карточка для каждой причины перечисляет скрытые политики:

```
[?] Analyzing LDAP Signing/Channel Binding via GPO (SYSVOL)... (Get-LDAPConfiguration)
[*] 4 finding(s) hidden:

Group:       Dormant policies - not linked
Reason:      Linked nowhere, so the settings reach no machine until the policy is linked.
Count:       3 policies
Policies:    Workstation Baseline V2              {11111111-1111-1111-1111-111111111111}
             DC Hardening V2                     {22222222-2222-2222-2222-222222222222}
             Member Server Baseline V2           {33333333-3333-3333-3333-333333333333}

[+] Found LDAP security configuration in 2 GPO(s):
    ... the active findings ...
```

**Сводка скрытых политик выводится первой, перед активными находками.** После строки `[?] Analyzing`
пользователь видит, что скрыто и почему, затем `[+] Found ...` — заголовок
действительно отображаемых находок. Строка `[+] Found` относится к объектам находок, не к
сводке скрытого, и располагается прямо над ними.

Каждая причина — одна **карточка**: серый объект в консоли, сворачиваемая карточка HTML,
изначально свернутая и отсортированная после реальных находок. Одна карточка на причину, не на
политику: для шестнадцати скрытых GPO достаточно двух-трёх карточек. Внутри карточки
слева имя политики, начиная с 45-го столбца GUID: нужны оба, поскольку имя узнаваемо,
а GUID задаёт папку `\\<domain>\SYSVOL\<domain>\Policies\`, которую нужно найти
в SYSVOL. Длинное имя сдвигает GUID вправо и не обрезается: по обрезанному
имени политику в SYSVOL нельзя было бы найти.

Сводная строка считает находки, а карточка — политики. Поэтому единица счёта указывается
(`on N GPO(s)`), если два числа различаются: десять значений реестра в одной непривязанной
политике дают одну строку в карточке. Непривязанные политики идут перед отключёнными:
первые — кандидаты на очистку, а вторые обычно намеренно выключены. Внутри карточки сортировка
по именам, чтобы два запуска по одному домену дали одинаковый порядок. Список не обрезается:
его длина ограничена числом политик домена; обрезка заставила бы использовать
`-IncludeInactive` только ради пропущенных имён, создавая гораздо больше вывода.

**Безопасные (не создающие доступа) настройки учитываются по имени и числу, а не печатаются полностью.**
Логика обратная опасным находкам: если adPEAS сообщает о праве или параметре, выданном тому,
кому его быть не должно, то ужесточающую политику стоит назвать в одной карточке,
а не создавать блок на каждое её значение. Используется такая же сводная карточка,
до активных находок, серая и свернутая в HTML. Обе проверки поддерживают
`-IncludeDefaults` (псевдоним `-IncludePrivileged`, который передаёт `Invoke-adPEAS`, поэтому подсказка
об этом доступна из полного сканирования) — ключ выводит эти параметры целиком:

```
[*] 10 assignment(s) only remove default holders - hardening, or a service about to break on 2 GPO(s) (-IncludeDefaults to list)

Group:       Assignments that only remove default holders
Reason:      Hardening more often than not, occasionally a service about to break - never a grant.
Count:       10 assignment(s) on 2 GPO(s)
Policies:    WSUS Baseline V1                    {44444444-4444-4444-4444-444444444444}
             DC Hardening V2                     {22222222-2222-2222-2222-222222222222}
```

- `Get-GPOUserRightsAssignment`: назначение, которое только *удаляет* штатных обладателей права. Правило появилось после того, как девять таких блоков предшествовали двум настоящим находкам.
  Если назначение одновременно добавляет *и* удаляет обладателей, сохраняется строка
  `RemovedFromDefault`: удалённые там — часть конечного набора правообладателей, а не отдельная находка.
  Удалённые субъекты составляют оставшуюся часть набора обладателей этого права, а не отдельную находку.
- `Get-GPOPointAndPrint`: настройка с оценкой *Hardened* либо *не управляет установкой
  драйверов*. Полный вывод содержал восемь зелёных строк, подтверждающих `Exploitability`.
  Случай User Configuration виден отдельно: Windows игнорирует такую настройку
  такую настройку (KB2307161), и риска здесь тоже нет, но ужесточение не применяется —
  это не то же самое, что действующая защита.

Как и для неактивных политик, строка считает находки, а карточка — политики:
несколько прав в одной GPO либо обе половины Point and Print могут давать разное число;
в этом случае указывается единица (`on N GPO(s)`).

Находки скрываются, а не удаляются. `-IncludeInactive` у отдельной проверки выводит все
неактивные находки серым, с полями `LinkedOUs` и `GPOStatus`, объясняющими причину.
Ключа намеренно нет у `Invoke-adPEAS`; подсказка о нём показывается только при прямом
запуске соответствующей проверки.

Три важных ограничения:

- Это относится к проверкам **параметров внутри** политики. Проверки учётных данных
  исключены: `cpassword` в `Groups.xml` читается Authenticated Users и без привязки
  GPO, поэтому применимость политики не влияет на факт утечки. `Get-GPOPermissions`
  тоже исключён: право редактировать неактивную политику важно, потому что её можно
  сначала изменить, затем привязать; `LinkedOUs` и `GPOStatus` всё равно выводятся.
- «Не привязано или не включено» определяется по каталогу: нет активных привязок либо
  соответствующая половина политики выключена. Это **не** итоговый RSoP. WMI-фильтр,
  никому не соответствующий, фильтрация безопасности по Apply Group Policy, Enforced и запрет
  наследования здесь не учитываются; политика, привязанная к пустой OU,
  считается активной.
- Если сведения о привязках не удалось прочитать, ничего не скрывается: провал перечисления
  означает неизвестное состояние, и находка не понижается из-за отсутствия данных.

Скрытие находки одновременно исключает её из HTML и JSON. Поэтому сравнение сканирований
покажет её исчезновение после отключения привязки.

**Толкование `EffectiveSetting`**: когда один параметр задан несколькими GPO, это поле показывает
какая политика определяет значение и почему. Ранее использовался логический `True`/`False`,
`IsEffectiveSetting`, не позволявший различить причины: `False` мог значить и
«политика с более высоким приоритетом переопределяет значение», и «эта политика не
затрагивает ни один компьютер» — совершенно разные задачи.

| Значение поля | Значение |
|-----------|-------|
| `Yes - wins precedence on the Domain Controllers OU` | Привязана к OU контроллеров домена или ниже и первая по порядку привязок. Именно это значение действует на DC. |
| `Yes - wins precedence at the domain root` | Привязана к корню домена, и политики OU контроллеров домена не имеют большего приоритета. |
| `Yes - wins precedence on its site` | Привязана к сайту DC, не выше самого контроллера домена. Политики сайта применяются раньше доменных, поэтому здесь определяют лишь то, что не задано доменом/OU, если привязка не принудительная (Enforced). |
| `Yes - applies on its linked OUs; no precedence comparison there` | Привязана к обычным OU и действует на их компьютеры. Важно: adPEAS не сравнивает порядок привязок ниже домена, поэтому две политики одной OU с противоположными значениями обе описываются так. |
| `Yes - applies below its links, but not on the domain controllers: ...` | Привязана выше контроллера домена, но контейнер на пути блокирует наследование и привязки не принудительны. Действует на другие компьютеры под своими привязками. |
| `No - overridden by '<name>' (link order <n>)` | Настроена и достигает компьютеров, но другая политика имеет приоритет. Для реального значения проверьте названную GPO. |
| `No - the policy is linked nowhere` | Настроена, но никуда не привязана: сейчас не меняет ничего; может быть удалена либо привязана. |
| `No - every link is disabled` | Привязана, но все связи выключены, поэтому ни на кого не действует. `GPOStatus` сообщает то же в отдельном поле. |

`EffectiveSetting` учитывает привязку, принудительное применение и порядок. Для проверок
подписи LDAP и SMB учитывается строка `reachesDomainControllers`, определяющая
реальное расположение компьютерных объектов DC, их сайты и контейнеры,
сайты и блокировка наследования. Отключена ли компьютерная часть политики —
отдельный вопрос, отражённый в `GPOStatus`.

### Get-GPOPermissions

**Назначение**: определяет, кто может изменять объекты групповой политики.

**Что проверяется**:
- Права записи на объекты GPO.
- Непривилегированные записи с правами редактирования GPO.
- Права записи в каталог каждой политики в SYSVOL (`Policies\{GUID}`), вторую часть GPO.
- Привязка GPO к критическим OU.
- Число затронутых компьютеров, включая контроллеры домена.
- Политики, у которых отсутствует каталог или `gpt.ini` в SYSVOL на читаемом DC: подсказка при активной привязке (если клиент не может открыть `gpt.ini` относящейся к нему политики, обработка групповых политик прерывается, событие 1058), примечание — если привязки нет. Наличие, но недоступность каталога обозначается как отказ чтения, а не как отсутствие.
- Каталоги в `SYSVOL\Policies` без соответствующего видимого данной учётной записи объекта политики: остаток удалённой политики либо политика, скрытая ACL объекта (примечание).
- Политика, которая нигде не применяется (нет привязок или они отключены), но широкая группа (Authenticated Users, Domain Users, Everyone и др.) может менять объект AD или его папку SYSVOL: строка `oneLinkAway` (подсказка) означает, что одной привязки достаточно для распространения внесённого содержимого.

**Влияние на безопасность**: изменение GPO даёт возможность выполнять код на всех компьютерах её области. Злоумышленник с правом записи GPO может развернуть вредоносный код по домену.

**Использование**:
```powershell
# По умолчанию: непривилегированные субъекты с правом изменения GPO
Get-GPOPermissions

# Включить привилегированных субъектов (Domain Admins, Group Policy Creator Owners и др.)
Get-GPOPermissions -IncludePrivileged
```

**Параметры**:

| Параметр | Описание |
|-----------|-------------|
| `-IncludePrivileged` | Включить привилегированные записи в вывод (жёлтая подсветка) |

**Возвращаемые свойства**:
- `VulnerableIdentity`: учётные записи с опасными разрешениями GPO.
- `Scope`: область GPO (DOMAIN-WIDE, Linked to X OU(s) или NOT LINKED).
- `LinkedOUs`: полные DN OU, к которым привязана GPO.
- `AffectedComputers`: число компьютеров, затрагиваемых GPO.

### Get-GPOLocalGroupMembership

**Назначение**: анализирует членство в локальных группах, заданное GPO.

**Что проверяется**:
- Добавление участников локальной Administrators через GPO.
- Добавление участников Remote Desktop Users.
- Изменения других привилегированных локальных групп.
- Каждый добавленный участник определяется по SID: широкая группа (Everyone, Domain Users и др.) повышает опасность назначения, а субъект Tier 0 и так имеет права группы и не помечается. Любой другой субъект — пользователь, группа домена, группа операторов — окрашивается по целевой группе (красный для Administrators и групп операторов; жёлтый для Backup Operators, Remote Desktop Users и сходных). Если назначение добавляет только Tier 0, оно является *примечанием*, кроме случая предварительной очистки всей группы.

**Влияние на безопасность**: добавление пользователей в локальные администраторы через GPO может обеспечивать постоянный привилегированный доступ на многих машинах.

**Использование**:
```powershell
Get-GPOLocalGroupMembership
```

### Get-GPOScheduledTasks

**Назначение**: оценивает задания, развернутые Group Policy Preferences (`ScheduledTasks.xml` в SYSVOL), по запускаемой программе и учётной записи выполнения.

**Что проверяется**:
- Каждое действие Exec обычных и немедленных задач в обоих форматах файлов и учётная запись запуска из элемента Preferences либо собственного principal задания.
- Задачи, выполняемые от SYSTEM, LOCAL SERVICE, NETWORK SERVICE или привилегированной записи.
- Программы, запускаемые из каталогов, файлы которых по умолчанию может менять каждый пользователь (`C:\Temp`, `C:\Users\Public` и др.) или куда может добавлять файлы (`C:\ProgramData`, `C:\Windows\Temp` и др.).
- UNC-пути: выполнение определяет тот, кто может писать в общий ресурс либо отвечать за имя его сервера. Разрешения записи ресурса не читаются: командные строки могут указывать общий ресурс как программу, аргумент, источник копирования или маску, и попытки их разбора давали много ошибок. Поэтому выполнение из ресурса — *подсказка*, если привилегии учётной записи не повышают её до находки.
- Задание от Tier 0 — *находка*. Задания от SYSTEM и операторских записей становятся *находками*, если программа лежит в общедоступно изменяемом по умолчанию каталоге; иначе — *подсказками*.
- Строки `cmd.exe /c` с незаключённым в кавычки путём к программе, содержащим пробел; cmd.exe делит такой путь по первому пробелу. Само поле программы планировщика не затронуто: Task Scheduler заключает его в кавычки.
- Задания из непривязанных или выключенных GPO сворачиваются в сводку; то же для элементов с действием Delete, которые только удаляют именованное задание и ничего не выполняют.

Пароль задания (`cpassword`) обнаруживает `Get-CredentialExposure`.

**Цвета консоли**: путь к программе (`Command`) подсвечивается жёлтым для всех исполняемых заданий и красным, если общедоступный каталог делает задание находкой; он входит в карточку задания, выполняемого с общего ресурса под SYSTEM, оператором или Tier 0. Запускающая запись (`RunAs`) красная для Tier 0, жёлтая — для операторов, SYSTEM, LOCAL SERVICE, NETWORK SERVICE. У каждой находки хотя бы одно из двух полей красное, поэтому красный заголовок соответствует красной строке. Полная причина (`RiskReason`) выводится только в HTML-карточке.

**Влияние на безопасность**: задание запускается на каждом компьютере области GPO. Кто может подменить программу для задания от SYSTEM, запускает код под SYSTEM на всех таких компьютерах; если оно запускается от привилегированной доменной записи, то с её правами (для Domain Admin — весь домен).

**Использование**:
```powershell
Get-GPOScheduledTasks

# Также показать задания непривязанных и выключенных политик
Get-GPOScheduledTasks -IncludeInactive
```

**Параметры**:

| Параметр | Описание |
|-----------|-------------|
| `-IncludeInactive` | Также перечислить задания непривязанных или выключенных политик |

### Get-GPOScriptPaths

**Назначение**: обнаруживает сценарии входа/выхода пользователя и запуска/выключения компьютера, раздаваемые GPO.

**Что проверяется**:
- Сценарии запуска/выключения компьютера (выполняются от SYSTEM в Machine).
- Сценарии входа/выхода пользователя (выполняются от имени пользователя).
- Сценарии, загружаемые через UNC (риск раскрытия учётных данных).
- Сценарии PowerShell из psscripts.ini.
- Кто может менять сценарий вне собственной папки GPO — NETLOGON, SYSVOL за пределами каталога GPO либо файловый ресурс. NTFS-права файла и его каталога читаются через SMB по имени домена и включённым компьютерам, причём только по DNS-имени из AD, никогда по короткому имени или IP/хосту, неизвестному домену. SYSVOL и NETLOGON по доменному имени читаются на DC текущего сеанса: запрос к самому `\\<domain>` потребовал бы билет Kerberos для `cifs/<domain>`, которого нет ни у одной учётной записи. Субъект помимо администраторов, способный писать туда, делает сценарий *находкой* и перечисляется в `scriptPathPermissions`; сценарий NETLOGON, изменяемый только администраторами, — *примечание*, а на другом сервере — *подсказка* (его администраторы определяют содержимое). Разрешения общего ресурса не читаются, локальные пути удалённо не проверяются.

**Влияние на безопасность**: сценарии GPO запускаются автоматически. Сценарии запуска/выключения выполняются от SYSTEM и могут привести к повышению привилегий; сценарии по UNC показывают учётные данные машины в сети.

**Использование**:
```powershell
Get-GPOScriptPaths

# Не устанавливать SMB-соединения с хостами из путей сценариев
Get-GPOScriptPaths -OPSEC
```

**Возвращаемые свойства**:
- `GPOName`: имя GPO, разворачивающей сценарий.
- `GPOGUID`: имя каталога GPO в SYSVOL.
- `GPOPath`: полный путь к этому каталогу.
- `SourceFile`: `scripts.ini` / `psscripts.ini`, из которого прочитана запись, относительно
  каталога GPO; не путать с `ScriptPath` ниже — это сам сценарий, на который
  ссылается .ini.
- `ScriptType`: Startup, Shutdown, Logon или Logoff.
- `ScriptPath`: путь к сценарию.
- `Parameters`: параметры сценария, если заданы.
- `ExecutionContext`: SYSTEM или User.
- `ScriptLanguage`: PowerShell, Batch, VBScript и др.
- `HasUNCPath`: загружается ли сценарий с общего ресурса.
- `scriptRisk`: значение расположения сценария для риска (хранилище GPO, NETLOGON, общий ресурс или локальный путь); кто может менять содержимое или почему право не проверено.
- `scriptPathPermissions`: одна строка `path: Identity (Rights)` на субъекта помимо администраторов с правом записи файла или каталога (выводится только при наличии).

### Get-GPORegistrySettings

**Назначение**: сообщает о значениях реестра, которые групповая политика задаёт в состоянии, допускающем атаку.

**Что проверяется**:
- Любое значение реестра, раздаваемое политикой, из трёх источников: административные шаблоны (`Registry.pol`), Group Policy Preferences (`Registry.xml`) и Security Options (`GptTmpl.inf`, раздел `[Registry Values]`).
- Проверка по фиксированному списку опасных параметров (`adPEAS-RegistryKeys.ps1`): кража учётных данных (WDigest, LM/NTLMv1, LM-хеши, больше десяти сохранённых входов вместо стандартных 10, делегирование CredSSP любому серверу), повышение привилегий (AlwaysInstallElevated в двух ветках, UAC), Kerberos и сертификаты (список исключений Zerologon, ESC10, DES/RC4 среди разрешённых типов шифрования), отключённые средства защиты (Defender, LSA protection, Credential Guard, брандмауэр, журналирование блоков сценариев), удалённый доступ (RDP, WinRM без шифрования или с Basic, незапрошенная Remote Assistance), SMB, подпись LDAP на клиенте, LLMNR и устаревшие протоколы, обновления через HTTP и Office-макросы без предупреждения (все версии и приложения Office).
- Только значения в опасном состоянии. Отсутствующая настройка усиления защиты не является находкой: политика, не задающая её, сама не ослабляет защиту. Элемент Preferences с действием удаления либо отключённый не разворачивает значение.

**Что не оценивается**: остальные параметры приложений и Windows без правил. Проверка считает их («N дополнительных значений реестра из M политик отсутствуют в списке этой проверки — не оценены»), а сообщение об отсутствии проблем формулируется «Через GPO не развёрнуты известные уязвимые значения реестра». Значения, которые оценивают другие проверки, не включаются в этот счёт: Point and Print (`Get-GPOPointAndPrint`), подпись SMB (`Get-SMBSigningStatus`), подпись LDAP и channel binding (`Get-LDAPConfiguration`), LAPS (`Get-LAPSConfiguration`) и строковые значения, похожие на пароль (`Get-CredentialExposure`). `-IncludeUnknown` выводит все прочие значения — по одному объекту на файл политики и по одной строке на значение; анализировать следует со специалистом по приложениям. Полное сканирование лишь подсчитывает их, для подробностей вызывайте проверку отдельно.

**Использование**:
```powershell
Get-GPORegistrySettings

# Также показать настройки непривязанных и выключенных политик
Get-GPORegistrySettings -IncludeInactive

# Также вывести все развёрнутые значения, которые проверка не оценивает, по файлам политики
Get-GPORegistrySettings -IncludeUnknown
```

**Возвращаемые свойства**:
- `GPOName`, `GPOGUID`, `GPOPath`, `SourceFile`: политика и её файл.
- `RegistryKey`: раздел реестра, ключ и имя параметра.
- `ConfiguredValue`: значение, записываемое политикой.
- `VulnerabilityName`, `RiskReason`: почему такое значение опасно.
- С `-IncludeUnknown`, по каждому файлу: `RegistryValues` — строка `hive\key\value = data` для каждого неоценённого значения без серьёзности. Длинные строки обрезаются после 100 символов; бинарное значение `Registry.pol` показывается как `(binary)`.

### Get-NonDefaultComputerOwners

**Назначение**: находит компьютеры, владельцы которых — непривилегированные пользователи, и явные разрешения вне Tier 0 на объектах компьютеров.

**Что проверяется**:
- Владелец объекта компьютера.
- Компьютеры, принадлежащие обычным пользователям вместо Domain Admins.
- ACE, записанные на самом объекте компьютера (не унаследованные), которые выдают субъекту вне Tier 0 полный контроль, GenericWrite, запись всех атрибутов или DACL, смену владельца, все расширенные права, сброс пароля либо запись `msDS-AllowedToActOnBehalfOfOtherIdentity`, `msDS-KeyCredentialLink`, `servicePrincipalName` или `dNSHostName`.
- ACE, которые класс компьютера создаёт для создателя записи, владельца, SELF и операторов, не выводятся; унаследованные ACE проверяются на OU, где задано делегирование.

**Влияние на безопасность**: владелец компьютера может менять объект, потенциально добавляя себя в `msDS-AllowedToActOnBehalfOfOtherIdentity` и открывая путь RBCD. Явная запись этого атрибута или `msDS-KeyCredentialLink`, сброс пароля и все расширенные права (включая чтение LAPS) аналогично могут привести к административному доступу к компьютеру.

**Использование**:
```powershell
Get-NonDefaultComputerOwners
```

### Get-ComputerPasswordAge

**Назначение**: находит активные компьютеры, у которых не обновляется пароль машинной учётной записи.

**Что проверяется**:
- Включённые компьютеры, входившие в домен за последние 30 дней (`-ActiveDays`), чей пароль компьютера старше 90 дней (`-PasswordAgeDays`).
- Рядовой компьютер и DC по умолчанию меняют пароль каждые 30 дней; отсутствие ротации означает выключенный `DisablePasswordChange`, стороннее средство присоединения без ротации или клонированный объект.
- Для контроллеров домена это *находка*, для прочих компьютеров — *подсказка*.

**Влияние на безопасность**: неизменный ключ машинной записи не устаревает. Получив его однажды, злоумышленник может подделывать сервисные билеты к узлу, а ключ DC позволяет реплицировать все хеши паролей домена.

**Использование**:
```powershell
Get-ComputerPasswordAge
Get-ComputerPasswordAge -PasswordAgeDays 60 -ActiveDays 14
```

### Get-NetworkMap

**Назначение**: сопоставляет IPv4-подсети активных компьютеров домена и их OU — показывает, где расположены компьютеры, не выполняя сетевого сканирования.

**Что выполняется**:
- Берутся включённые компьютеры со входом за последние 30 дней (`lastLogonTimestamp`, `-ActiveDays`). Атрибут реплицируется с задержкой 9–14 дней, поэтому меньшее окно пропустит используемые компьютеры.
- Разрешается DNS-имя (`dNSHostName`) только внутри DNS-домена: компьютер может сам писать этот атрибут, поэтому внешние имена подсчитываются без разрешения.
- Адреса берутся из интегрированных с AD зон DNS, прочитанных по LDAP с подключённого DC (`Get-DomainDNSZone`, `Get-DomainDNSRecord`): все адреса имени, без DNS-запроса. Если имя отсутствует, оно разрешается запросом только к DC (`-DnsServer` сеанса или адресу DC), не к посторонним серверам.
- Один объект на /24-подсеть: число компьютеров, DC, серверов и клиентов, самая узкая подсеть из Sites and Services, содержащая адрес, с её сайтом («Not in Sites and Services», если нет), а также DN каждой OU/контейнера с числом соответствующих компьютеров. Список самих компьютеров не выводится.
- Подсети, заданные в Sites and Services без активных компьютеров, выводятся одним объектом после /24: известные сети без увиденных компьютеров (например, пул VPN, DMZ, сеть устройств). Заданная подсеть внутри одной из /24 отдельно не выводится: её покрывает соответствующая /24.
- Подсчитываются случаи без отображения: имена вне домена, отсутствие DNS-имени или пригодного IPv4 (loopback, APIPA, multicast) и компьютеры только с IPv6. IPv6 не отображается.

Подсеть с DC отмечается как *подсказка* (сеть Tier 0) и не повышает оценку риска.

**Параметры**:
- `-ActiveDays <n>`: допустимый срок с последнего входа (по умолчанию 30 дней).
- `-ExportTargets <file>`: записать подсети в файл — CIDR по строке: сначала /24, затем заданные подсети без активных компьютеров. Это список целей для сканера (`nmap -iL` либо `Get-Content <file> | Invoke-PortScan`); существующий файл перезаписывается. Полный аудит файл не создаёт.
- `-OPSEC`: без DNS-запросов; компьютеры, отсутствующие в зонах DNS, учитываются как неотображённые.

**Использование**:
```powershell
Get-NetworkMap
Get-NetworkMap -ActiveDays 60 -ExportTargets .\subnets.txt
```

## <a id="application-module"></a>Модуль Application

Анализирует инфраструктуру корпоративных приложений.

### Get-ExchangeInfrastructure

**Назначение**: перечисляет инфраструктуру серверов Exchange.

**Что проверяется**:
- Наличие организации Exchange (msExchOrganizationContainer).
- Версии Exchange через LDAP-атрибуты и опрос HTTP-интерфейсов.
- Состояние Extended Protection for Authentication (EPA) для веб-интерфейсов Exchange.
- Членство в Exchange Trusted Subsystem (высокопривилегированные служебные записи).
- Членство в Exchange Windows Permissions (может иметь DCSync через WriteDacl на корне домена).
- Членство в Organization Management (полные полномочия администратора Exchange).

**Влияние на безопасность**: Exchange часто имеет расширенные права в AD. Exchange Windows Permissions по умолчанию располагает WriteDacl на корне домена, что может использоваться для DCSync. Члены Exchange Trusted Subsystem могут изменять объекты Exchange. Для устаревших версий Exchange известны уязвимости ProxyLogon и ProxyShell. Отсутствие EPA позволяет атаки ретрансляции NTLM на веб-интерфейсы Exchange.

**Использование**:
```powershell
Get-ExchangeInfrastructure
```

---

### Get-SCCMInfrastructure

**Назначение**: перечисляет инфраструктуру SCCM/MECM с помощью LDAP-запросов к AD.

**Что проверяется**:
- Наличие контейнера System Management.
- Коды сайтов SCCM и иерархия по объектам AD `mSSMSSite`.
- Management Points и тип сайта (CAS, Primary, Secondary) по `mSSMSManagementPoint` с разбором XML capabilities.
- Выявление серверов SCCM по SPN (SMS*, SMSSQLBKUP*).
- Число клиентов SCCM по SPN CmRcService (масштаб возможного компрометационного воздействия).
- Серверы загрузки PXE/WDS (объекты connectionPoint, intellimirrorSCP).
- Служебные учётные записи SCCM.
- Группы безопасности SCCM.

**Влияние на безопасность**: SCCM развёртывает ПО на всех управляемых системах. Центральный сайт CAS контролирует всю иерархию и является активом Tier 0. PXE-серверы могут использоваться для кражи учётных данных или подмены развёртывания ОС. Число клиентов SCCM характеризует возможный масштаб последствий компрометации.

**Использование**:
```powershell
Get-SCCMInfrastructure
```

---

### Get-SCOMInfrastructure

**Назначение**: перечисляет инфраструктуру SCOM.

**Что проверяется**:
- Серверы управления SCOM.
- Конфигурация агентов.
- Учётные записи RunAs.

**Влияние на безопасность**: агенты SCOM работают на множестве систем с правами локального администратора. Учётные записи RunAs часто избыточно привилегированы; их захват открывает путь к перемещению между компьютерами.

**Использование**:
```powershell
Get-SCOMInfrastructure
```

## <a id="shares-module"></a>Модуль Shares

Ищет общие ресурсы компьютеров домена. **Не входит в обычное сканирование** — запустите с
`-Module Shares` либо вызовите `Invoke-ShareHunt` отдельно.

### Invoke-ShareHunt

**Назначение**: находит ресурсы, которые текущая учётная запись может читать, и ищет на них учётные данные.

**Почему исключён по умолчанию**: модуль устанавливает SMB-соединение с каждым компьютером
Windows домена и читает найденные общие ресурсы. Это наиболее заметное сетевое действие adPEAS,
которое может обнаружить мониторинг, поэтому запуск — отдельное решение оператора,
а не поведение по умолчанию. `-OPSEC` полностью пропускает его.

**Что выполняется**, четыре ограниченных этапа, рассчитанных и на большие домены:

1. **Компьютеры**: включённые компьютеры Windows со входом за последние 30 дней
   (`-ActiveDays`) по `dNSHostName` — только в пределах DNS-имени домена, поскольку
   компьютер может сам менять этот атрибут. Либо компьютеры, заданные через
   `-ComputerName` или конвейер: имя, список имён или объекты функций
   `Get-Domain*`, у которых берётся `dNSHostName`. Явно указанное имя не сверяется
   с доменным суффиксом DNS — оператор указал его намеренно. Пустой конвейер
   не сканирует ничего и не переключается на весь домен; например,
   `Get-DomainComputer -OperatingSystem '*Server 2012*' | Invoke-ShareHunt` при отсутствии
   таких компьютеров не начинает сканировать всё подряд.
2. **Доступность TCP 445**: один проход с общим сроком ожидания на *блок* узлов, не на узел;
   несколько сотен недоступных адресов расходуют один тайм-аут на каждый блок, а не
   на каждый адрес.
3. **Их общие ресурсы** перечисляются через `NetShareEnum` уровня 1 — доступного обычной
   учётной записи — в пуле runspace с одним предельным сроком всей операции.
   Иначе узел, завершивший TCP handshake, но зависший на RPC, задержал бы работу
   на десятки секунд. Из них проверяются только дисковые ресурсы, без системных
   ресурсов Windows (`-IncludeAdmin`), различаемых по системному флагу, имени
   и форме административного ресурса диска, и без SYSVOL и NETLOGON, которые
   `Get-CredentialExposure` проверяет вместе с породившей файл политикой (`-IncludeSysvol`).
   У каждого ресурса проверяется право перечислить его корень. **Скрытые** ресурсы
   исследуются: символ $ в конце имени означает отсутствие в обзоре сети, а не
   административные права. `Software$` и `Profiles$` — обычные скрытые ресурсы.
4. **Читаемые ресурсы** обходятся в ширину: файлы с паролями часто близки к корню.
   Четыре ограничения: глубина 10 (`-MaxDepth`), 50 000 файлов
   (`-MaxEntries`), 600 секунд на ресурс (`-ShareTimeoutSeconds`), 60 минут на все
   (`-MaxMinutes`). Первые два значения выбраны достаточно большими: малый ресурс
   заканчивается гораздо раньше, а файловый сервер важнее всего. Файлы свыше 1024 КБ
   (`-MaxFileSizeKB`) учитываются, но не читаются. Каталоги из `-ExcludeFolder`
   пропускаются на всех ресурсах наряду с всегда исключаемыми папками Windows
   (`Windows`, `WinSxS`, `Program Files`, `Program Files (x86)`, `ProgramData`,
   `$Recycle.Bin`, `System Volume Information`, `Recovery`, `PerfLogs`) — исключение
   помогает не тратить лимит на бесполезные разделы. Все отобранные файлы анализируются
   теми же функциями, что используются для SYSVOL: GPP, Winlogon, файлы ответов,
   пароли VNC, строки `net use` и присваивания паролей обнаруживаются одинаково.

**Ход выполнения**: консоль показывает одну строку прогресса по шести фазам:
поиск активных компьютеров, проверка 445 (со счётчиком ответивших), перечисление общих
ресурсов, проба каждого ресурса, сбор файлов ресурса и поиск по каждому файлу.
Для фаз отдельного ресурса нет порога количества: один зависший узел может занять
столько же времени, сколько 30 исправных. Индикатор показывает, какого узла ждут;
поиск считает все ресурсы вместе, чтобы показывать общую долю завершения.
поскольку пользователю важна доля выполненного поиска по всем ресурсам.

**Экспорт**: `-ExportShares <file>` записывает читаемые ресурсы, по одному UNC на строку,
для дальнейшей работы и передачи в другие инструменты. `-ExportFindings <file>` сохраняет весь результат в JSON:
лимиты запуска, недоступные объекты, каждый читаемый ресурс и глубину его обхода,
все находки с именами файлов и расшифрованными значениями. Файл результатов создаётся,
даже если ничего не найдено: пустой результат — тоже результат, а лимиты необходимы
для сравнения с новым запуском. **В JSON содержатся учётные данные в открытом виде**,
потому что они найдены. При вызове `Invoke-adPEAS -Outputfile` обращайтесь с ними как с секретными данными:
те же строки входят в обычный текстовый, HTML и JSON-отчёт;
два специальных параметра нужны для отдельного вызова.

**`-ShareName`**: исследует ресурсы указанного имени вместо перечисления опубликованных,
сразу открывая `\\<computer>\<name>`. Это быстрее и помогает, когда сервер запрещает
`NetShareEnum` (Win32 5), но доступ к самому ресурсу разрешён — распространённая конфигурация.
Указанное имя принимается независимо от типа ресурса, поэтому
`-ShareName C$` не требует `-IncludeAdmin`, а `-ShareName SYSVOL` — `-IncludeSysvol`.
Имена буквальные: список не получается, поэтому маску подставить некуда; задавайте несколько имён.

**`-ListSharesOnly`**: останавливается после списка доступных для чтения общих ресурсов —
файлы не читаются, учётные данные не ищутся. Удобно для первого прохода по незнакомому
домену, когда нужен лишь ответ «где вообще искать»; время ограничено проверкой
доступности и перечислением. Отчёт явно пишет, что содержимое не прочитано, чтобы
отсутствие найденных паролей не было принято за результат полной проверки.

**Непроверенные области**: каждый достигнутый предел и каждый пропуск подсчитываются:
компьютеры вне доменного имени или без него, неответившие узлы, узлы без доступного
перечня ресурсов (с причиной), административные ресурсы и SYSVOL, ресурсы, которые
можно перечислить, но нельзя читать, недоступные файлы, файлы больше лимита.
Ресурс, обход которого прерван, содержит `notFullySearched` с причиной; если строки нет,
ресурс обойдён полностью. Сообщение об отсутствии находок — *примечание*, но никогда
не «безопасно»: проверено ровно столько, сколько позволили права и лимиты.

**Влияние на безопасность**: пароль в сценарии либо файле настроек общего ресурса
читают все, кому разрешён сам ресурс, — часто гораздо больше людей, чем следовало бы
допускать к учётной записи; в отличие от SYSVOL, такой доступ редко пересматривают.

**Использование**:
```powershell
Invoke-ShareHunt
Invoke-ShareHunt -ComputerName fs01.contoso.com, fs02.contoso.com -MaxDepth 8
Invoke-ShareHunt -ActiveDays 14 -MaxMinutes 20
Invoke-ShareHunt -ListSharesOnly
'fs01.contoso.com' | Invoke-ShareHunt -ListSharesOnly
Get-DomainComputer -OperatingSystem '*Server*' | Invoke-ShareHunt
Invoke-ShareHunt -ComputerName fs01.contoso.com -ShareName Finance
Invoke-ShareHunt -ShareName Finance, 'Profiles$'
Invoke-ShareHunt -ExportShares .\shares.txt -ExportFindings .\shares.json
Invoke-PortScan -Target 10.1.2.0/24 -Port 445 -PassThru | Invoke-ShareHunt
Invoke-ShareHunt -ComputerName fs01.contoso.com -ExcludeFolder Archive, 'Build Output'
Invoke-adPEAS -Module Shares
```
